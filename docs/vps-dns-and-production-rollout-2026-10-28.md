# DNS VPS и обновление панели на основном роутере

После [серверного расследования](vpn-server-timeout-investigation-2026-10-28.md)
пользователь отдельно разрешил исправления VPS и обновление `192.168.50.1`.
На двух проверяемых VPS, DE/FI, применены постоянные настройки DNS. Панель
`.1` обновлена с RC1 до проверенного ARM64 CI-артефакта. Xray, AdGuard,
маршруты и firewall на `.1` не перезапускались и не перенастраивались.
Это перенос тестовой сборки по отдельному запросу, а не выпуск стабильной версии.

## Применённые настройки VPS

```text
nameserver 1.1.1.1
nameserver 8.8.8.8
options timeout:1 attempts:2
```

DE использует `resolvconf`: независимый резервный nameserver и options
добавлены в `/etc/resolvconf/resolv.conf.d/base`, затем выполнен `resolvconf -u`.
Первый nameserver интерфейса и search domain сохранены. Настройка внесена в
[постоянный источник генерации resolver](https://manpages.debian.org/bookworm/resolvconf/resolvconf.8.en.html#libc),
а не только в файл под `/run`.

FI использует статический resolver и Docker с host network. В файле хоста и
DNS-строке `/etc/network/interfaces` оставлены два работоспособных IPv4 upstream;
недоступный IPv6 upstream удалён. В Compose сохранены
[`dns` и `dns_opt`](https://docs.docker.com/reference/compose-file/services/#dns)
для последующего пересоздания контейнера. Файл resolver работающего контейнера
обновлён через `docker exec`; контейнер не пересоздавался. Его текущий
HostConfig ещё не содержит новых Compose-полей, однако работающий Xray уже
видит новые nameserver/options. Постоянные файлы и runtime resolver проверены.

На каждом VPS перед изменением сохранены исходные файлы, их режимы и план
отката в `/root/ruopenray-backups/dns-reliability-20261028/`, каталог 0700,
копии 0600. Независимый watchdog был готов вернуть DNS через 300 с при
незавершённой проверке; после DNS/HTTPS-контролей изменения подтверждены.
Для ручного восстановления оставлен `dns_engine.py rollback` в том же каталоге.

PID и конфигурации обоих Xray сохранены. Не менялись Reality, sniffing,
finalRules, ключи, подписки, маршруты и параметры TCP ядра. Системный DNS VPS
и прямой DoH AdGuard на роутере — разные участки цепочки; настройки AdGuard
этим исправлением не менялись.

## Контроль после исправления DNS

По 100 прямых HTTPS-запросов с каждого VPS к Cloudflare/gstatic, лимит 8 с;
сохранялись DNS/TCP/TLS-фазы. Отдельные настоящие DE/FI VPN-клиенты на `.117`
чередовали три HTTPS-цели, по 90 запросов, с тем же лимитом.

| Проверка | Успех HTTPS | Максимум всего запроса | Максимум DNS |
| --- | --- | --- | --- |
| Непосредственно DE VPS | 99/100 | 8001 мс, неудачный запрос | 1007 мс |
| Непосредственно FI VPS | 100/100 | 1572 мс | 1020 мс |
| VPN через DE с `.117` | 90/90 | 1261 мс | Удалённый DNS не выделен этой метрикой |
| VPN через FI с `.117` | 90/90 | 6026 мс | Удалённый DNS не выделен этой метрикой |

В неудачной прямой DE-пробе DNS занял **4,6 мс**, затем TCP подключался около
**6,8 с**, а оставшегося времени не хватило для TLS. Таким образом, DNS
разрешился во всех 100 DE-пробах, но транспортные сбои DNS-настройкой не
устранены. У FI сохраняется один медленный VPN-ответ. Timeout 1 с относится
к попытке resolver, а не ко всему HTTPS-запросу или всем повторам Xray.
Короткие серии не заменяют длительную приёмку и не доказывают отсутствие
будущих таймаутов.

## Что установлено на `.1`

- OpenWrt **24.10.4**, ARM64, opkg. Применена замена исполняемого файла панели;
  x86_64 APK тестового `.117` на этот роутер не устанавливался.
- Версия панели: **`0.5.1-test.447+1c0ef96`**, API **0.2.0**.
- Source: **`1c0ef96b2dbea131b1d743d0f672af53ffc8c0ae`**.
  Исполняемый Go/frontend-код совпадает с источником проверенного SDK r9
  `223dac9`; последующие изменения до `1c0ef96` добавляли тесты и recipe.
- Артефакт взят из [успешного CI](https://github.com/AceAsket/RuOpenRay/actions/runs/40753033188),
  где прошли Go/race/vet/frontend, настоящие Xray-туннели на трёх версиях и
  сборка пяти архитектур. Это CI-сборка, новый релизный тег не создавался.
- Проверен официальный SHA-256 ZIP артефакта, ARM64/revision в Go build info,
  автономный `--self-check` на самом роутере и SHA загруженного процесса.
  SHA-256 binary:
  `051e1f59bc645ac4eeb4f32d8032ebe74b8c318b569253684ddff95f70778fb6`.

До замены сохранены прежний binary и архив настроек, профилей, конфигураций
DNS/Xray/network/firewall/DHCP, init и cron. Архив скачан и сверен по SHA-256;
копия на роутере: `/root/ruopenray-backups/panel-rc4-20261028/`.
Замена через rename выполнялась на файловой системе назначения. Отдельный
watchdog был готов вернуть прежний binary при отсутствии подтверждения в
течение 150 с. Проверка новой панели и связи завершилась за **7,8 с**, после
чего обновление подтверждено.

Сохранены active config, отсутствие draft, профили, пароли/настройки,
DNS/filter settings, PID Xray/AdGuard, policy rules/routes и nft ruleset.
Обычный рост access/error logs не считается изменением настроек. API draft
0.2 добавляет поля ревизий и activeConfig; сравнивались прежнее содержимое и
отсутствие черновика, а не буквальное равенство старого и нового набора полей.
Встроенные frontend-ресурсы загружены с `.1` и сравнены с Git source.
Xray остаётся **26.10.21**; ядро не обновлялось.

Перед заменой и сразу после неё прошли по шесть DNS-проверок UDP/TCP и по три
HTTPS-проверки: Discord, GitHub и прямой сайт. Затем выполнены **16 раундов
за 301,7 с** со свежими DNS-именами и двумя HTTPS-целями:

| Проверка `.1` | Результат |
| --- | --- |
| DNS UDP/TCP | 32/32 |
| Discord HTTPS | 16/16 |
| GitHub API HTTPS | 12/16 |
| Все проверки одновременно | 12/16 раундов |
| PID панели/Xray/AdGuard, сеть, готовность UI | Сохранены во всех раундах |

Это успешное обновление панели с сохранением состояния, но **не полностью
успешная сетевая приёмка**. Рабочая VPN-цепочка `.1` и настройки AdGuard
остались прежними.

## Отдельно найденная проблема GitHub и фрагментации

В дополнительном контроле curl через рабочий SOCKS `.1` получено 7/8 ответов;
один запрос завершился exit 56, OpenSSL `wrong version number` при чтении
после TLS handshake. Для этих новых проб сохранены код выхода, stderr и
времена, в отличие от двух старых событий исходного harness.

Изолированно на `.117` сравнивался один и тот же используемый для GitHub
VLESS/Reality-профиль с исходным freedom fragmentation и без него. В каждом
варианте — по 40 запросов к GitHub API, без изменения рабочего профиля `.1`.

| Вариант | Получен HTTP-ответ | Ошибки транспорта |
| --- | --- | --- |
| Fragmentation включена | 35/40: 17 HTTP 200, 18 HTTP 403 | 2 `bad record MAC`, 3 таймаута |
| Fragmentation выключена | 40/40: 32 HTTP 200, 8 HTTP 403 | 0 |

HTTP 403 учитывается отдельно и не объявляется успешным ответом приложения;
при этом он подтверждает завершённый TLS и получение HTTP. Эта короткая
серия указывает на отдельную проблему используемой цепочки fragmentation,
но не доказывает отсутствие всех проблем без неё. Рабочую цепочку `.1`
не меняли: её изменение требует отдельной проверки конфигурации и применения
с кратким перезапуском Xray. Исправлять её изменением DNS VPS оснований нет.

## Завершение и открытые вопросы

Временные probes и четыре изолированных Xray `.117` остановлены, проверенные
task-owned каталоги VPS/`.117` удалены после сохранения результатов.
Тестовых SOCKS listeners не осталось. На VPS повторно проверены постоянные
DNS-файлы, runtime resolver, PID и конфигурации Xray. На `.117` сохранены
active config/draft, контрольные хеши и PID рабочих служб. На `.1` повторно
проверены новая версия, конфигурация, DNS/фильтры, сеть и PID Xray/AdGuard.
Резервные копии и сценарии отката оставлены на целевых машинах.

Остаются отдельная проверка и применение исправления fragmentation, разбор
оставшихся DE TCP-задержек, новая длительная приёмка и остальные пункты
[плана аудита](reliability-implementation-plan.md). Результаты предыдущих
серий 26/31 и 28/31 не пересчитываются и не заменяются данным переносом.
