# Таймауты VPN: проверка со стороны серверов

Продолжение [расследования](network-timeout-investigation-2026-10-28.md) и
[приёмки RC4 r9](reliability-acceptance-rc4-r9-2026-10-28.md). Доступ к двум
действительно используемым DE/FI VPS найден в соседнем чате
«Проверить финский адрес CloudThree». SSH-подключения выполнены с проверкой
сохранённых ключей хостов. Учётные данные, адреса VPS, профили и сырые captures
в репозиторий не включены.

На этом этапе штатные конфигурации и службы VPS, `.117` и `.1` не менялись.
На `.1` выполнялись только чтение и ограниченный по времени пассивный захват
WAN, передаваемый непосредственно на диагностический компьютер. Временные
клиенты `.117` использовали отдельные loopback-порты и копии профилей.

## Что установлено

Есть как минимум два разных механизма задержки:

1. **DNS на самих VPS:** потерянные/поздние ответы UDP upstream вызывают
   примерно пятисекундное ожидание. Это воспроизведено запросами непосредственно
   с VPS, отдельно от VPN и AdGuard роутера.
2. **Внешнее TCP-соединение до DE:** в пойманном таймауте WAN-сторона роутера
   ждала около 7,1 с установления TCP, затем ещё около 7,3 с первого TLS-ответа.
   Когда полный ClientHello дошёл до VPS, ответ последовал через 5,4 мс.
   Обработка в Xray/nginx не объясняет эту многосекундную задержку.

Это не устанавливает причину каждого исторического сбоя и не определяет
конкретного оператора связи, который задержал/потерял пакеты.

## Состояние VPS

На обоих серверах работает Xray **26.10.21**, сборка Go 1.27.3. DE запускается
службой x-ui, FI — в Docker с host network. В собранных журналах и снимках
не обнаружены OOM или перезапуски Xray в проверяемом интервале; оснований
связывать пойманный сбой с нехваткой CPU/RAM не найдено. Это наблюдение
ограничено интервалом диагностики.

Уровень журналирования warning, access log выключен: восстановить старые
соединения по историческому debug-журналу невозможно. Для новых событий
собраны пакеты и временные отметки отдельных клиентов.

В обоих freedom-выходах используется системное разрешение имён; отдельный
блок Xray DNS отсутствует. Настроены finalRules с запретом private IP.
В этой версии [проверка finalRules может разрешать домен системным resolver
перед dial](https://github.com/XTLS/Xray-core/blob/v26.10.21/proxy/freedom/freedom.go#L275-L325).
Удалять защиту от private IP ради скорости не требуется.

DE использует единственный IPv4 resolver `1.1.1.1`. У FI перед ним также
записан IPv6 resolver, хотя глобального IPv6/default route нет. Обращение к
этому IPv6-адресу немедленно даёт `Network is unreachable`; именно оно
не объясняет пятисекундные ожидания, но конфигурацию стоит привести
в соответствие реальной сети. Resolver внутри контейнера FI проверен отдельно.

## DNS: прямые контрольные запросы

Одинаковый статический Go-клиент с проверкой TLS-сертификата обращался к
Cloudflare/gstatic. На FI исходная серия выполнена внутри того же контейнера.
В IP-контроле сохранены прежние SNI и HTTP Host, меняется только адрес dial.
Лимит HTTPS — 8 с, отдельного UDP DNS — 6 с.

| Проверка | DE | FI |
| --- | --- | --- |
| HTTPS по домену, исходный resolver | 40/40; максимум 5028 мс | 40/40; максимум 5032 мс |
| Из них время DNS в медленной пробе | 5006 мс | 5015 мс |
| HTTPS по закреплённому IP, без VPN | 40/40; максимум 278 мс | 40/40; максимум 1456 мс |
| Свежие UDP DNS к IPv4 upstream | 30/30; максимум 22 мс | 29/30; один таймаут 6000 мс |

В capture есть запросы A/AAAA без своевременного ответа, повторы спустя
примерно 5 с и отдельные ответы примерно через 7 с. Таким образом, задержка
системного DNS доказана независимо от TLS/Reality. Не доказано, на каком
именно участке теряются DNS-пакеты: upstream, сеть хостинга или транзит.

### Проверенный вариант resolver, пока без применения

В **отдельном mount namespace** процесса проверен такой файл:

```text
nameserver 1.1.1.1
nameserver 8.8.8.8
options timeout:1 attempts:2
```

Bind mount существовал только в namespace временного процесса; системный
файл и файл контейнера не переписывались. Это проверка варианта конфигурации,
а не изменение действующего Xray.

При намеренно молчащем первом DNS и рабочем втором выполнено по два HTTPS
запроса на каждом VPS для каждого значения таймаута. Все ответы успешны:
с `timeout:5` — около **5,04–5,06 с**, с `timeout:1` — около **1,04–1,13 с**.
Это время именно данного сценария, а не общий верхний предел DNS при любых
отказах и повторах.

С реальными двумя resolver FI прошёл **50/50** HTTPS-запросов, максимум 1028 мс;
DE — **49/50**. В неудачной DE-пробе DNS занял лишь **4,4 мс**, задержка была
на TCP/TLS целевого соединения. Поэтому замена resolver не устраняет все
сетевые таймауты и не является основанием объявить VPN исправным.

Для применения нужно сохранить настройку в источнике конфигурации
resolvconf/развёртывания Docker и отдельно проверить resolver уже работающего
процесса. Редактирование только сгенерированного файла может быть потеряно.
В этой диагностике постоянные настройки не применялись, контейнеры не
пересоздавались и Xray не перезапускался.

## Поправка к предыдущему IP-контролю FI

У FI включён sniffing `http/tls/quic`, `routeOnly` отсутствует. В такой схеме
[Xray заменяет адрес назначения доменом из sniffing](https://github.com/XTLS/Xray-core/blob/v26.10.21/app/dispatcher/default.go#L281-L297).
Следовательно, прежняя передача IP через SOCKS при сохранённом TLS SNI
**не исключала удалённый DNS**. Вывод «закрепление IP не помогло, значит DNS
исключён» был бы неверен; предыдущий отчёт уточнён.

Это не противоречит прямому IP-контролю выше: тот клиент работает на VPS без
передачи запроса через sniffing-вход. Сам по себе sniffing также не доказывает
пятисекундную задержку; её подтверждают прямые DNS-замеры и пакеты.

## VPN и синхронный захват TCP

Изолированные клиенты `.117` использовали настоящие DE/FI-профили с закреплённым
IP самого VPS, исходным Firefox fingerprint и без добавления fragmentation.
В каждой серии чередовались Cloudflare, gstatic и HTTPS по IP `1.1.1.1`;
лимит — 8 с на запрос. Рабочий профиль `.117` не переключался.

| Путь | Первая серия | Вторая серия |
| --- | --- | --- |
| DE | 86/90 | 89/90 |
| FI | 90/90, четыре ответа дольше 4 с | 90/90, один ответ дольше 4 с |

Для второй серии есть captures на `.117`, WAN `.1` и VPS. Корреляция внешнего
TLS выполнена по одному и тому же ClientHello random, а не только по близкому
времени: на DE одновременно присутствовал другой пользовательский трафик.
Проверяемые подключения к VPS в access log `.1` направлялись direct;
вложенный VPN для них не обнаружен.

DE, запрос 52 второй серии, начало **2026-10-28 20:15:54 UTC**:

- Клиент `.117` передал полный внешний ClientHello сразу; локальный TCP
  к прозрачному обработчику `.1` установился менее чем за 1 мс.
- На WAN `.1` от первого SYN до передачи ClientHello прошло **7139 мс**;
  видны повторы SYN.
- От первой передачи ClientHello на WAN до получения TLS-ответа там же прошло
  ещё примерно **7332 мс**. На VPS видны повторные SYN/SYN-ACK и позднее
  поступление ACK/ClientHello. Эти интервалы определены в пределах часов
  одной машины, поэтому не зависят от синхронизации часов двух серверов.
- VPS отвечал на полученный SYN за **0,1 мс**, на полный ClientHello — за
  **5,4 мс**; локальный nginx на 9443 — за **1,7 мс**.
- Клиентская HTTPS-проба уже завершилась по лимиту **8 с**. Последующая
  готовность внешнего туннеля не превращает её в успешную.

Для этого события задержка находится на внешнем TCP-пути, включая возможные
участки egress роутера, оператора и сети VPS, а не в многосекундной обработке
ClientHello самим Xray/nginx. По endpoint captures нельзя достоверно назвать
конкретный промежуточный узел или объявить это DPI. Отключение TLS-защиты,
смена fingerprint или удаление finalRules этим результатом не обоснованы.

Другие медленные запросы второй серии имели быстрое внешнее TLS-соединение
и около пяти секунд внутри него. Это согласуется с найденными DNS-задержками
VPS, но каждому зашифрованному запросу не приписывается отдельный DNS-пакет
без достаточной корреляции.

## Сохранность и дальнейшие действия

Все task-owned probe, DNS-drop и отдельные Xray завершены. Проверенные
временные каталоги хостов, контейнера FI и `.117` удалены после сохранения
доказательств. Проверены неизменность PID Xray, конфигураций и resolver обоих
VPS. На `.117` active config, draft, контрольные хеши Xray/UI/DNS/DHCP/network/
firewall и PID Xray/AdGuard сохранены; заключительные DNS и живой SOCKS успешны.
Временных SOCKS listeners не осталось. `.1` не обновлялась и не перезапускалась.

Следующая проверяемая работа:

1. Применить устойчивую конфигурацию DNS VPS через её постоянный источник,
   с резервной копией и откатом; подтвердить настройку работающего Xray и
   повторить native DNS/VPN-серии. Не отключать private-IP protection.
2. Для оставшегося DE TCP-сбоя сравнить независимый путь/точку выхода и
   повторить двусторонний capture. Текущие данные достаточны для локализации
   вне обработки TLS VPS, но недостаточны для обвинения конкретного провайдера.
3. Повторить длительную приёмку после изменений. Исходные **26/31** и
   последующие r9 **28/31** остаются историческими результатами; новые короткие
   серии не заменяют их полностью успешной приёмкой.

Эта работа не разрешает перенос на `.1` и не закрывает остальные пункты
[плана аудита](reliability-implementation-plan.md).
