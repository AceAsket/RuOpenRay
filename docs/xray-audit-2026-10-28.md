# Проверка после обновления Xray до 26.10.21

Проверки выполнены на отдельном OpenWrt-стенде с Xray 26.10.21 и контрольным
26.3.27. Рабочее ядро не заменялось: для сравнений использовались отдельные
процессы с временными конфигурациями. На основном шлюзе выполнялись чтение
конфигурации, native validation и диагностические запросы; новые маршруты и
DNS-настройки в рамках этого аудита не применялись.

## Исправления в Git

- Удаление пустых `sniffing.domainsExcluded` при сохранении/проверке конфига
  и защита обновления ядра: коммит `730cbca`. Его CI успешно проверил Xray
  26.3.27, 26.9.9 и 26.10.21. Подробности —
  [разбор причины и воспроизведение](xray-sniffing-exclusions.md).
- Внешняя подборка `discordFull` дополнена точным хостом
  `full:cdn.localizeapi.com` в [RuOpenRay-scenarios](https://github.com/AceAsket/RuOpenRay-scenarios).
  Это скрипт локализации главной страницы Discord. Обновление источника
  обновляет шаблон, но само не меняет действующие пользовательские правила.
- `TestXraySniffingDestinations` добавлен в CI: он проверяет HTTP Host, TLS SNI
  и оба значения `routeOnly`, когда исходный IP отличается от ответа DNS Xray.

Основные конфигурации, PID служб, firewall и policy routing стенда сравнивались
до и после сетевых тестов. Временные правила, namespace и процессы удалены;
состояние восстановлено. Проверка действующего конфига основного шлюза проходит,
пустых исключений больше нет.

## Почему HTTP 200 главной страницы недостаточно

HTML Discord загружался примерно за 0,5 секунды, но браузер оставался с пустой
страницей: синхронный `cdn.localizeapi.com/localize.js` не завершал загрузку.
AdGuard этот хост не блокировал. На двух адресах CDN, выбранных DNS Xray, все
шесть прямых запросов получили HTTP 200 и остановились примерно после 24 КБ
из 86 782 байт. Через VPN все шесть завершились за 0,36–1,46 секунды.

Первоначальная проверка с DNS самого клиента давала другие CDN-адреса и могла
ошибочно показать исправный direct. Сравнение нужно проводить с тем же SNI,
IP назначения и полным чтением тела. Одни заголовки или TCP connect этого не
показывают. Точное место ограничения на прямом пути этой проверкой не установлено.

После отдельного разрешения пользователя на короткий перезапуск 28 октября
добавлен только этот хост в существующее правило Discord через VPN. Проверка
после применения дала восемь полных загрузок скрипта за 0,36–0,50 секунды,
видимую главную страницу в новой вкладке и HTTP 200 от API Discord. Данные
DNS/AdGuard, ядро, firewall и прочие изменения черновика сохранены; создана
резервная копия. Также доступно [веб-приложение Discord](https://discord.com/app).

## Дополнительно: нестабильность одного VPN-профиля

Повторные загрузки `https://telegram.org/` выявили ошибки обработки TLS-записей
через проверенный немецкий VLESS/REALITY-профиль с фрагментацией. При сравнении
менялось только клиентское ядро; профиль и его связанный fragment-outbound
сохранялись. Для каждого варианта создавались новые соединения, сертификаты
проверялись, тело ответа читалось до конца.

| Выход | Xray 26.3.27 | Xray 26.10.21 |
| --- | --- | --- |
| Нидерланды, рабочий профиль Discord | 5/5 | 5/5 |
| Германия, текущая фрагментация | 3/5; две ошибки TLS record | 3/5; две ошибки TLS record |
| Тот же немецкий профиль без фрагментации | 5/5 | 3/5; два таймаута |

Это отдельная нестабильность пути/профиля, а не доказанная регрессия только
26.10.21: ошибки с фрагментацией воспроизводятся и на 26.3.27. Пять запросов
не доказывают постоянную исправность остальных вариантов. Отключать фрагментацию
для всех профилей или откатывать рабочее ядро по этим данным нельзя.
Существующая диагностика TLS в панели умеет сравнивать профиль с фрагментацией
и без неё, сохраняя рабочие настройки. Перед изменением маршрута Telegram или
другой группы нужен отдельный проверенный черновик; в этом аудите маршруты
не переключались.

## Границы проверки

Это проверка перечисленных сценариев и конкретных выходов, а не гарантия
доступности всех сайтов. Ответ 200 на HTML не проверяет все динамические
зависимости. Публичные IPv6 и HTTP/3, RTC/голос Discord и реальный мобильный
LAN-клиент в этом повторном аудите отдельно не подтверждались. Ранее выявленные
ограничения native IPv6 TPROXY и Vision/UDP 443 описаны в
[пилоте B4](b4-pilot-2026-10-06.md).

Диагностика фрагментированного профиля обязана включать его связанный
`dialerProxy`-выход. Без него отдельный пробный конфиг может пройти синтаксическую
проверку, но давать ложные сбои соединения. Сравнение фрагментации должно менять
только этот параметр и использовать несколько новых TLS-соединений.
