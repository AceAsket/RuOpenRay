# Полный инженерный аудит RuOpenRay — 28 октября 2026

Проверена ветка `dev`, коммит `3661ce226111d6cb01895986f9d72c37a4bd6d02`,
тег `v0.5.1-rc3`. Отдельно прочитан каталог `RuOpenRay-scenarios` на коммите
`74211a61d4062096642c462ad89e9f349f6e3737`.

**Вывод: RC3 пригоден для дальнейших испытаний, но стабильную 0.5.1 пока выпускать
рано.** Основной долг — одинаковые гарантии безопасности для всех способов
изменить конфигурацию. Сейчас обычное применение, активация профиля, смена
сервера подписки, geo-обновление и фоновые команды ведут себя по-разному.

Аудит охватывает backend/API, авторизацию, конфигурации/профили/черновик,
обновления, подписки, маршрутизацию/балансировщики, DNS/AdGuard, B4/AWG,
firewall, резервные копии, ресурсы, frontend, установку и CI. Это обзор всех
основных подсистем с подробной проверкой опасных путей, а не доказательство
отсутствия любых ошибок в каждой строке. Сетевые службы и файлы на `.1`/`.117`
не изменялись; новые нагрузочные, аварийные или сетевые испытания там не запускались.

Этот документ расширяет [первоначальную очередь RC3](project-audit-2026-10-28.md).
Ниже явно различаются локальное воспроизведение, вывод из кода и незакрытая
приёмка на OpenWrt. Проверки, воспроизводящие дефект, не означают его исправление.

## Находки, которые нужно закрыть

Приоритет P1 — до стабильного выпуска либо до включения затронутой функции
в поддерживаемый сценарий. P2 — следующий этап надёжности и удобства. Приоритет
не означает, что сбой сейчас наблюдается на рабочем роутере.

### A01 · P1 · Активация профиля обходит проверки записи активного конфига

**Подтверждено локально.** `profiles.go:260` читает JSON и записывает исходные
байты через `withAdGuardBootstrap`. В этом пути нет `validateConfig`,
нормализации sniffing, `validateB4DirectCandidate` и `b4ControlMu`, которые
есть при обычной записи (`xray_service.go:38`).

Два воспроизведения: старый профиль возвращает `domainsExcluded:[""]` прямо
в активный файл; профиль с зарезервированной меткой B4 на VLESS принимается,
хотя обычный B4 validator его отвергает. Возврат пустого исключения способен
вернуть уже исправленную несовместимость с новым ядром. Вторая ситуация
нарушает гарантию, что очередь B4 получает только выбранный direct-трафик.
Фактический перехват пакетов этим аудитом не проверялся.

**Сделать:** единый путь нормализации, native validation, проверки интеграций,
резервирования и записи для активации профиля. Явно разделить сохранённый
и реально загруженный ядром профиль; сейчас активация сама не перезапускает
Xray. Проверить старые профили после миграции и импорт невалидного JSON Xray.

### A02 · P1 · Неудачное применение удаляет черновик и отображается как успех

**Подтверждено с инъекцией ошибки перезапуска и отдельным frontend-сценарием.**
`applyConfig` (`xray_service.go:201`, очистка на строке 239) вызывает
`clearConfigDraft()` и при `restart.ok=false`. При возврате HTTP 200 с
`ok:false` `web/config-actions.js:44` всё равно устанавливает
`appliedConfigText`, снимает `serverDraftExists` и может показать
«Конфигурация применена». HTTP-клиент проверяет HTTP-статус, но не `ok`.

**Сделать:** при ошибке сохранять черновик, показывать отказ и результат отката;
сбрасывать dirty-state только после подтверждённого успешного применения.
Откат и проверка службы должны иметь собственный итоговый статус. Добавить
backend/frontend-тесты отказа записи, перезапуска и самого отката.

### A03 · P1 · Нет общей транзакции и защиты от устаревшего черновика

**Потеря более нового черновика воспроизведена; окна конкурирующих операций
подтверждены структурой кода, сетевой инцидент не воспроизводился.**
`config_draft.go:43` не проверяет ревизию и пишет `os.WriteFile`; устаревший
клиент успешно заменяет более новый черновик. Отдельные mutex для B4, AdGuard,
backup и core-update не покрывают всю последовательность read → validate →
backup → write → restart → verify. Cron/CLI создают другие процессы и вообще
не разделяют эти mutex. Есть также чтения/запись `cfg.Password` без общего
замка; race detector в текущий CI не включён.

**Сделать:** общий координатор изменений, ревизия/хеш исходного состояния,
compare-and-swap черновика и атомарная запись. Предусмотреть межпроцессный
lock для cron/CLI; одного `sync.Mutex` недостаточно. При apply удалять только
ту версию черновика, которая действительно применена. Добавить конкурентные
API-тесты и Linux `go test -race`.

### A04 · P1 · Cron/CLI используют другой путь активного конфига

**Разрешение пути и создание другого конфига воспроизведены локально;
последующая перенастройка UCI на OpenWrt следует из кода и здесь не выполнялась.**
Cron в `geo_schedule.go:91`, `route_presets.go:632` и
`subscription_schedule.go:84` не передаёт `RUOPENRAY_ACTIVE_CONFIG`.
`loadAppConfig` (`config.go:97`) без него выбирает `<DataDir>/config.json`,
а пакет/установщик обслуживают `/etc/xray/config.json`. До разбора CLI-команды
`main` вызывает `ensureData` и при отсутствии файла создаёт другой default config.

Для geo это особенно существенно: `runScheduledGeoUpdate` → `updateGeo` →
`serviceAction("restart")` → `enableXrayServiceConfig`, где UCI conffiles
устанавливается в `s.cfg.ActiveConfig`. Следовательно, при стандартной
раздельной раскладке путей успешная фоновая geo-загрузка может направить
управляемый сервис на другой конфиг. Автообновление подписок сейчас запускается
с `applyActive=false, restart=false`; приписывать ему такой перезапуск нельзя.

**Сделать:** единый загрузчик UCI/env для daemon и CLI, передавать все значимые
пути, не создавать default config для служебных read/update-команд. Тестировать
cron с окружением реального OpenWrt и с нестандартными путями.

### A05 · P1 · Geo-файлы принимаются без проверки формата и без безопасной замены

**Подтверждено локально.** `geo_upload.go:17` принимает текстовый `invalid.dat`
и заменяет им `geosite.dat`. `geo_update.go:366` принимает HTTP 200 с HTML
крупнее 1 КиБ и устанавливает его как DAT. Download-путь использует
неограниченный `io.ReadAll` и пишет прямо в целевой файл; пары geoip/geosite
не имеют общей транзакции. Upload-путь использует временный файл, но формат
DAT и совместимость текущего конфига до замены не проверяет.

`ParseMultipartForm(128 MiB)` задаёт порог хранения в памяти, а не ограничение
всего HTTP-body. Поэтому последующий LimitReader одного файла не ограничивает
расход памяти/tmp во время предшествующего разбора multipart.
Это следует из [контракта net/http](https://pkg.go.dev/net/http#Request.ParseMultipartForm).
Исчерпание RAM/диска нагрузочным тестом не вызывалось.

**Сделать:** лимит всего body до parsing, потоковая загрузка с жёсткой верхней
границей, проверка DAT и всех нужных категорий, staging полного набора,
native config validation, обязательный rollback и только затем restart.
HTML, частичная загрузка, ENOSPC и пропажа категории должны сохранять старые базы.

### A06 · P1 · Самообновление и shell-установка не сверяют SHA-256 панели

**Подтверждено чтением полного пути загрузки.** `app_update.go:183` проверяет
HTTP и минимальный размер, затем заменяет исполняемый файл. Опубликованный
`.sha256` и digest release asset не проверяются. При использовании зеркала
оно фактически становится источником доверенного исполняемого кода.
Ошибки создания опционального backup игнорируются, подтверждения здоровья
новой панели и автоматического отката после restart нет. Аналогично
`scripts/install-openwrt.sh:183` проверяет только непустой файл.

Это отличается от обновления Xray: там уже есть официальный digest, staged
binary, обязательная копия и откат. Проверка опубликованных RC3-артефактов
при выпуске не заменяет проверку на устройстве при каждом обновлении.

**Сделать:** единая проверка checksum из доверенного release metadata независимо
от зеркала, размера и архитектуры; обязательная восстанавливаемая копия;
health-check новой панели и аварийный rollback из отдельного процесса/службы.
Обрабатывать переполнение лимита загрузки и одновременные запросы обновления.

### A07 · P1 · Применение firewall удаляет рабочую таблицу до проверки новой

**Подтверждено кодом, аварийный запуск на роутере не выполнялся.**
`firewall.go:554` сначала пишет постоянный nft-файл и hotplug, затем делает
`nft delete table inet ruopenray`, затем `nft -f`. При отказе загрузки
автоматического восстановления прежней таблицы/файлов/policy routing нет.
Compatibility preflight не является `nft --check`. Hotplug из
`internal/firewall/firewall.go` повторяет delete-before-load и завершает
скрипт с нулём после подавления ошибок. Отсутствие перехвата может затронуть
как доступность VPN, так и ожидаемое ограничение выхода напрямую.

**Сделать:** проверить candidate установленным nft, подготовить атомарный
nft batch, сохранять/восстанавливать конфиг, policy routes и DNS-настройки как
одну операцию. Не считать любой `not found` успешным результатом любой команды;
обработать допустимое отсутствие отдельно. Проверить отказ nft, reload/ifup,
занятые marks/tables и ENOSPC на `.117`.

### A08 · P1 · Смена сервера подписки теряет dialerProxy и расходится с профилем

**Подтверждено локально.** `subscriptions.go:104` при ручном выборе использует
`CloneOutboundWithTag`, а refresh-путь — вариант с сохранением dialerProxy.
При выборе кандидата существующая привязка к fragmentation/другому dialer
исчезает. Сохранённый активный профиль остаётся со старым сервером; повторная
активация профиля возвращает его. В ручном выборе и
`applySubscriptionActiveOutbounds` (`subscriptions.go:450`) нет
`syncCurrentProfile`. Простой `restoreBackup` также не синхронизирует профиль.

**Сделать:** явно сохранять пользовательские transport overlays, согласованно
обновлять active config, subscription store и активный профиль, откатывать все
три при отказе. Проверить ручной выбор, refresh, fallback, последующую
активацию профиля и восстановление. Дубли адрес/порт с разными UUID/transport
проверить отдельно при сопоставлении кандидатов.

### A09 · P1 · Фильтр inline SVG пропускает кодированные активные URL

**Обход фильтра подтверждён на Go и JS; выполнение JavaScript в браузере
не проверялось.** `route_presets.go:166` и `web/route-visuals.js:125` фильтруют
SVG регулярными выражениями. Ссылка со схемой, закодированной HTML entity,
проходит оба фильтра и попадает в возвращаемую HTML-разметку. При разборе
браузером сущности декодируются. Внешний каталог/пользовательский SVG — вход
для этой разметки; считать его безопасным на основании этих regex нельзя.

**Сделать:** разрешающий список SVG-элементов/атрибутов с разбором документа,
запрет ссылок, активных элементов, анимаций и внешних ресурсов либо отображение
непроверенного SVG в изолированном контексте изображения. Добавить browser-тесты
entity/namespace/malformed SVG и защитный CSP. В официальном каталоге вредоносная
иконка не обнаружена; компрометация источника не заявляется.

### A10 · P1 · SDK-пакет устарел и имеет небезопасный пароль по умолчанию

**Подтверждено файлами пакета; реальная SDK-сборка не запускалась.**
`packaging/openwrt/Makefile` указывает версию 0.3.5, mutable `main` и корень
Go-модуля, в котором нет Go-файлов, вместо `cmd/ruopenray-ui`.
Пакетная UCI-конфигурация и init используют `0.0.0.0:9090` и пароль `admin`;
postinst не генерирует пароль. Shell installer генерирует пароль отдельно —
это не исправляет пакетный путь. Наличие такого дефолта не означает, что
пароль `admin` установлен сейчас на `.1` или `.117`.

**Сделать:** исправить build target, версию и immutable ref, внедрить версию
в бинарник; для нового устройства генерировать пароль/требовать первичную
настройку. Сертифицировать install/upgrade/remove в SDK с сохранением данных,
зависимостями и разными layout. До этого не обещать поддержанный IPK.

### A11 · P2 · Срок сессии обходится in-memory map; нет серверного logout

**Истечение срока воспроизведено.** Login добавляет remember-token в
`sessions`; `authed` (`api.go:499`) сначала доверяет наличию в map и лишь затем
проверяет подпись/expiry. Просроченный token в map принимается. В map нет TTL
и удаления отдельных сессий. Выход UI удаляет browser storage, но серверный
токен не отзывает. Ограничение частоты входа отсутствует.

**Сделать:** server-side TTL и revoke/logout, ограничение количества сессий
и частоты входа, отдельный случайный signing key вместо пароля как HMAC key.
Нужны тесты bearer/cookie до/после expiry, logout и смены пароля.
Доступ по HTTP остаётся ограничением текущей LAN-схемы; для удалённого доступа
нужен явно поддержанный HTTPS/proxy-режим. WAN для панели здесь не открывался.

### A12 · P2 · Ошибки JSON игнорируются и могут стирать данные

**Подтверждено локально.** POST с обрезанным JSON на `/api/routing/names`
возвращает 200 и стирает существующие имена: `api.go` игнорирует ошибку
`readJSON`, `route_names.go:60` сохраняет пустой map. Та же форма
`payload, _ := readJSON(...)` распространена в других изменяющих handlers;
их последствия нужно проверить по контракту каждого endpoint.

**Сделать:** единая проверка JSON/типа/обязательных полей, ответы 400/413 без
записей, различать пустое значение и отсутствие поля. Проверить names,
disabled rules, metadata, расписания, profiles, service и integration endpoints.

### A13 · P2 · При ошибке проверки конфига интерфейс остаётся занят

**Подтверждено отдельным JS-сценарием.** `web/config-actions.js:14` ставит
`configTesting=true`, но не снимает его в `finally`. При HTTP/сетевой ошибке
Promise.all отклоняется; кнопки отмены и применения остаются disabled.

**Сделать:** `try/catch/finally`, сохранение введённых данных, видимое сообщение
с повторной проверкой. Аналогично проверить все busy-state и незавершённые fetch
при переходах между вкладками. Не связывать исправность UI с доступностью GitHub.

### A14 · P1 · Успешный restart/живой PID не доказывают рабочий VPN/DNS

**Подтверждено границами реализации, новый сетевой отказ не воспроизводился.**
`restartSubscriptionWithRollback` принимает успех init-команды без ожидания
готовности процесса. Core-update дополнительно ждёт стабильный PID, но не
проверяет передачу DNS/HTTPS. Поэтому сценарии «init вернул 0, процесс вскоре
завершился» и «процесс жив, транспорт не работает» покрыты не полностью.

**Сделать:** одинаковые проверки готовности для apply/profile/subscription/
server-mode/core update, baseline до операции, проверка после, несколько
независимых целей и полное чтение небольшого контрольного ответа. Внешний
отказ одного сайта отличать от регрессии после изменения. Не добавлять
автооткат по единственному недоступному домену.

Разделить TLS/headers/full-body, проверять статус согласно назначению пробы; 403 и 200 с незавершённым body не равны доступному приложению. Объяснение маршрута по черновику не выдавать за факт из running Xray. |
| B03 / P2 | B4: политика QUIC и реальный DPI | `b4_direct.go:98` ставит UDP в очередь только для первых 9 пакетов направления соединения. При стратегии reject это не постоянный запрет последующих QUIC-пакетов. Проверить повторные Initial, conntrack, drop/reject, fallback TCP и restart firewall. На `.1` B4 автоматически не ставить. |
| B04 / P2 | Native IPv6 LAN-перехват и kill switch | Генератор использует IPv4 sets, `tproxy ip`, `ip rule` и route `0.0.0.0/0`. IPv6 через outbound не доказывает перехват LAN IPv6. Нужны отдельный inbound/policy routing, DNS и dual-stack acceptance; до этого явно показывать границу поддержки. |
| B05 / P2 | Ресурсы маленьких роутеров | У full-backup лимит 128 МиБ, содержимое restore и предыдущие версии держатся в памяти; обновление ядра также одновременно держит ZIP/распакованный binary/копию. `GOMEMLIMIT=48MiB` — мягкая цель GC, не жёсткий предел ([документация Go](https://pkg.go.dev/runtime#hdr-Environment_Variables)). Измерить RSS/tmp/flash на реальной нижней границе RAM, потоково обрабатывать большие файлы, проверять место до операции. |
| B06 / P2 | Политика хранения копий | JSON-backup создаётся перед каждым apply/refresh. Сейчас есть ручная очистка каталога, а автоматической квоты/retention нет. Ввести срок/число/лимит размера и сохранять последнюю пригодную копию и копию текущей операции. Проверить cleanup одновременно с update/restore, чтобы не удалить нужный rollback. |
| B07 / P2 | Восстановление на чистой VM | Path traversal/duplicates/symlink/integrity и write-failure rollback уже тестируются. Нужен повторяемый restore на другой подготовленной OpenWrt, reboot и чтение всех служб/групп/подписок. Архив не является образом прошивки, не содержит binaries/geo/native B4. Откат при ошибке записи не гарантирует восстановление после потери питания. |
| B08 / P2 | CI и контракты окружений | Добавить Linux race, fuzz для share links/DNS/backup/catalog, негативные API-контракты, browser E2E настоящего Go backend. Node mock ранее предлагал downgrade RC3→RC2, Go его отклоняет. Обновление Actions/Node и закрепление сторонних Actions выполнить отдельной проверкой; govulncheck запускать регулярно. |
| B09 / P2 | Server-mode/AWG acceptance | ACL, WAN firewall и runtime имеют unit-тесты и отдельные действия. Server-mode apply всё ещё имеет отдельную последовательность сохранения/restart/очистки черновика (`server_mode.go:544`); включить в A02/A03/A14. Managed AWG runtime поддерживает только direct WAN egress, а другой outbound блокирует с объяснением: это незакрытая возможность, а не обещанная работающая цепочка. |
| B10 / P2 | UI, API и наблюдаемость | Ошибки интеграций не должны стирать формы или выглядеть здоровьем всей системы. Единый контракт ok/error/retryable/operation ID; после таймаута API должна быть возможность узнать, завершилась ли операция. Проверить мобильные ширины, keyboard/focus dropdown, сохранение форм при background refresh и отмену длительной диагностики. |
| B11 / P2 | Предсказуемость failover | Настройки и recovery всех стратегий проверяются real Xray CI. Но Observatory использует один общий URL; его отказ может переключить исправный канал. Нужны длительное наблюдение, ясный shared scope и экспериментальные сценарии сетевых сбоев. Порог ошибок и задержку возврата не обещать, пока они не реализованы поддерживаемым механизмом ядра. |
| B12 / P2 | Документация DNS и каналов выпуска | Свести схемы AdGuard DoH-direct / relay-via-Xray с актуальными ограничениями; direct DNS сохранять независимым от VPN. Не переносить AdGuard на 53 ради client IP без отдельной смены архитектуры. Для RC документировать установщик конкретного тега и версию binary; `main`/stable Latest могут оставаться старее `dev`. |

## Что уже имеет полезные гарантии

- Настоящие VLESS gRPC+TLS/Trojan TLS, отрицательные credentials/certificates,
  sniffing и recovery стратегий проверяются отдельными Xray-процессами в CI.
- Native core update сверяет официальный digest, проверяет candidate core
  и конфиг, делает обязательную копию и откатывает binary при отказе активации.
- AdGuard upstream editor проверяет кандидатов, сравнивает исходный список
  до/после сетевой проверки, сохраняет domain-specific записи и не затирает
  распознанное стороннее изменение при откате. Это хорошая модель для других форм.
- Анализатор дублей/пересечений ограничивает объём работы, показывает неполноту
  и не удаляет правила автоматически. Неизвестные geo/regexp/DNS отмечены.
- Для групп есть постоянные ID и закрепление общего маршрута; исправлять нужно
  пути сохранения/обновления, а не снова объединять правила только по названию.
- Full backup имеет manifest/hashes, предел числа файлов, проверку путей,
  отказ на symlink и откат при ошибках записи. Ограничения VM/power-loss остаются.

## Очередь реализации и приёмка

1. **Пакет надёжности конфигураций:** A01, A02, A03, A08, A12, A13.
   Сначала regression-тесты ожидаемого исправленного поведения, затем общий
   координатор. После backend/UI тестов — только `.117`.
2. **Фоновые задания и geo:** A04, A05. Проверить действительный cron env,
   невалидные/обрезанные данные, лимиты и ENOSPC. Не запускать реальные задания
   на `.1`, пока не подтверждено сохранение её layout и config path.
3. **Обновление и защита:** A06, A09, A11, A14. Проверить trusted checksum,
   rollback панели из отдельного процесса, SVG browser cases и lifecycle сессий.
4. **Firewall и доставка:** A07, A10. Изолированная OpenWrt VM, действительный
   nft/policy routing, SDK build, install/upgrade/remove, reboot/ifup/reload.
5. **Длительная приёмка RC:** опубликованный binary и SHA, DNS UDP/TCP при
   остановленном Xray в режиме direct DoH, реальные VPN TLS 1.2/1.3 с полным
   телом, failover/возврат, restore на второй VM, повторный reboot. Сначала
   серии с контролируемыми отказами, затем наблюдение не менее суток как
   первоначальный критерий; отсутствие ошибок сутки не доказывает их невозможность.
6. **Стабильная 0.5.1:** блокирующие P1 закрыты либо затронутые возможности
   явно исключены из поддерживаемой установки; smoke опубликованного артефакта
   пройден на `.117`. Только после этого готовить отдельное обновление `.1`
   с копией, сохранением её черновика и согласованным окном перезапуска.
