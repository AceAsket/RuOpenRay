# Аудит интерфейса установки и обновления RuOpenRay

Исправления по этому аудиту внесены и проверены 4 ноября 2026 года:
[результаты исправления и приёмки](ui-install-update-fixes-2026-11-04.md).
Ниже сохранены исходные замечания к базе `97e2644`; диагностические probes
воспроизводят прежние дефекты и не являются тестами исправленной версии.

Дата: 4 ноября 2026 года. Проверенная база: `dev`, `97e2644`, версия панели `0.5.2`.
Стенд: `192.168.50.117:9090`, OpenWrt `25.12.4`, x86/64, Xray `26.10.31`.

Выявлены 14 замечаний: 4 с приоритетом P1 и 10 с приоритетом P2.
Основные риски — секреты в диагностическом экспорте, потеря профилей,
сброс настроек при повторной установке и отсутствие автоматического отката
в рекомендуемом shell-пути обновления.

P1 означает риск раскрытия секрета, потери данных или недоступности действующей
установки. P2 означает неработающий пользовательский сценарий либо сообщение,
которое существенно расходится с фактическим состоянием.

## Область проверки

Проверены формы настроек, профили, быстрый запуск, применение конфигурации,
обновления панели, Xray и geo, shell installer, OpenWrt packaging, LuCI launcher
и соответствующие инструкции. Статические выводы сверены с вызываемым backend,
а воспроизводимые проверки выполнялись с реальными функциями проекта и
изолированными данными.

На стенде выполнены вход, просмотр интерфейса и проверка существующего черновика
через Xray. Уже при входе был баннер пяти неприменённых изменений. Применение,
обновление, переустановка, переключение профиля и перезапуск служб не запускались.
Продуктовый код в рамках аудита не изменён.

## Замечания P1

### U01 Экспорт без секретов сохраняет пароль DoH

**Сценарий.** Добавить DoH сервер с Basic Auth через интерфейс DNS, оставив
область доменов пустой. Скачать профиль кнопкой «Скачать без секретов» либо
обезличенную конфигурацию. Строка вида
`https://audit-user:audit-password@dns.google/dns-query` остаётся в `dns.servers`
полностью, хотя экспорт содержит `anonymized: true` и обещание маскировки.
При отправке такого файла для диагностики раскрывается пароль DNS провайдера.

**Причина и доказательство.** `dns-actions.js:44` встраивает учётные данные в URL,
`dns-model.js:52` допускает строковое представление. `redactString()` в
`config-actions.js:260` меняет теги, но сохраняет прочие строки. Экспорт профиля
в `profile-actions.js:83` использует ту же функцию. Воспроизведён полный путь
`createDnsActions.addDnsServer → anonymizeConfig` на синтетическом пароле.

**Исправление.** Маскировать userinfo в URL независимо от ключа и вложенности.
Отдельно проверить чувствительные HTTP заголовки. Добавить проверку экспорта
именно для поддерживаемого интерфейсом DoH Basic Auth.

### U02 Создание и переименование могут уничтожить профиль

**Сценарии.** Создать разные профили с предложенными формой именами «дом» и
«работа»: оба сохраняются как `-.json`, второй заменяет первый без предупреждения.
Другой путь: открыть `work`, переименовать в `work.json`, сохранить. Сначала
записывается `work.json`, затем тот же файл удаляется как старый профиль `work`.
Интерфейс сообщает об успешном сохранении.

**Причина и доказательство.** `profiles.go:100` заменяет всё вне ASCII набора
на `-` и добавляет `.json`. `saveProfileConfig()` в `profiles.go:198` записывает
результат без проверки коллизии. `profile-actions.js:51` сравнивает исходные
имена, а удаление выполняет после записи. Пример с русскими именами предлагает
сама форма в `aux-panels-view.js:149`. Удаление при `work → work.json`
воспроизведено реальным action с файловым хранилищем в памяти.

**Исправление.** Отделить отображаемое имя от ID; нормализовать имя на сервере
до проверки коллизии. Выполнять переименование одной серверной операцией,
запрещать неявную замену и учитывать совпадение канонических имён.

### I01 Повторная установка сбрасывает параметры действующей установки

**Сценарий.** Установить панель с нестандартным адресом, портом, каталогом данных
или активным Xray конфигом. Выполнить рекомендуемую в `README.md:350` команду
переустановки без повторной передачи всех прежних переменных окружения.
Параметры вернутся к defaults: `0.0.0.0:9090`, `/etc/ruopenray-ui`,
`/etc/xray/config.json`, сервис `xray`. Привязка только к loopback также теряется.

**Причина.** `scripts/install-openwrt.sh:7` задаёт defaults; из существующей
конфигурации сохраняется пароль. В строке 264 удаляется вся UCI секция `main`.
`enable_xray_service_config()` в строке 725 дополнительно меняет `conffiles`
и удаляет `confdir` у Xray. Если прежняя установка использовала другую схему
конфигурации, следующий запуск Xray может прочитать другой набор настроек.
Вывод подтверждён чтением полного пути установки; на стенде переустановка
с изменёнными параметрами не выполнялась.

**Исправление.** Подхватывать текущие значения перед применением defaults,
отдельно учитывать явно переданные overrides. Повторная установка панели
должна сохранять действующие пути и схему конфигурации Xray.

### I02 Shell обновление не восстанавливает прежний бинарник после отказа

**Сценарий.** Повторно установить панель через shell installer с кандидатом,
который имеет правильный SHA-256, но не запускается в целевой среде. Скрипт
заменяет установленный бинарник, не подтверждает работоспособность панели
и завершается ошибкой. Для восстановления требуется SSH и ручное возвращение
сохранённой копии.

**Причина.** `scripts/install-openwrt.sh:224` создаёт копию и выполняет `mv`.
Проверки `--self-check` и запуска safe updater здесь нет. В строке 749
проверяется пароль процесса, но не выполняется rollback при отказе. Этот путь
не вызывает защищённый `updateApp` с его журналом и watchdog. Наличие проверки
SHA и backup само по себе не обеспечивает возврат работоспособной версии.
Вывод статический; аварийное обновление стенда не запускалось.

**Исправление.** Использовать единый механизм безопасного обновления либо
добавить проверку кандидата, ожидание готовности и обязательный откат.

## Замечания P2

### I03 Первое ядро Xray невозможно установить из GitHub

В мастере выбрать установку Xray из GitHub на устройстве без `/usr/bin/xray`.
После подготовки кандидата `replaceCoreTransaction()` безусловно читает
прежний файл (`core_update_safe.go:98`) и возвращает ошибку отсутствия файла.
Активация не вызывается. Интерфейс предлагает этот путь и для отсутствующего
ядра (`setup-view.js:764`). Изолированный Go probe подтвердил `os.IsNotExist`
и ноль вызовов активации; установка через пакетный менеджер этим выводом
не затрагивается.

Нужно отдельно обрабатывать первую установку: фиксировать отсутствие прежнего
бинарника и при откате удалять кандидата, возвращая исходное состояние.
Также требуется подготовить init/UCI новой установки: текущая активация при
`running=false` сразу возвращает успех (`core_update_safe.go:219`). До появления
полного сценария можно направлять первую установку в пакетный мастер.

### M01 Панель показывает готовность до завершения обновления

Backend возвращает `ok:true, state:pending` до окончания независимой проверки
(`app_update.go:267`). `updates-actions.js:44` сохраняет этот ответ, снимает
`appUpdating` и планирует один `refresh` через 2,5 секунды. `settings-view.js:320`
показывает «Готово». Существующий `/api/app/update-status` (`api.go:423`)
не опрашивается. Поздний `rolled_back` или `rollback_failed` не отражается
в результате операции; после успешного обновления документ со старым JS
автоматически не перезагружается.

Probe с настоящими actions и `settingsPanel()` подтвердил состояние `pending`,
надпись «Готово», доступную кнопку обновления и отсутствие запроса итогового
статуса. Нужно опрашивать статус до конечного состояния, показывать откат и
ошибку восстановления, затем безопасно перезагружать интерфейс с учётом форм.

### U03 Форма локальных прокси сбрасывается до чтения значений

В «Настройки → Прокси для приложений» изменить порт SOCKS5 с `10808` на `10999`
и нажать «Обновить черновик Xray». Общий обработчик вызывает `render()` до action
(`action-bindings.js:187`, `:219`). Форма строится заново из старого конфига
(`settings-view.js:147`), после чего `saveLocalProxyDraft()` читает уже старые
значения (`xray-draft-actions.js:318`). Сообщение об успехе скрывает потерю ввода.
Это касается также адресов, включения и учётных данных SOCKS5/HTTP.

Полный сценарий сохранения воспроизведён локальным probe с настоящими view,
binding и action: введено `10999`, сохранено `10808`. На стенде сброс этого же
ввода подтверждён кнопкой «Проверить черновик», без записи нового черновика.
Нужно хранить редактируемые значения в state либо захватывать их до перерисовки.

### U04 Выбор профиля не переключает работающий Xray

Кнопка выбора профиля вызывает `/api/profiles/activate`. Сервер проверяет
профиль, пишет активный файл и маркер, возвращает `restartRequired:true`
(`profiles.go:292`, `:308`). `profile-actions.js:9` игнорирует этот флаг,
показывает «Активирован профиль» и обновляет данные. Новый файл становится
baseline интерфейса, поэтому при отсутствии другого черновика баннер применения
не появляется. Работающий процесс Xray продолжает использовать прежний конфиг.

Probe воспроизвёл один запрос activate, отсутствие restart/apply и отсутствие
баннера изменений. Нужно выбирать профиль в черновик с явным применением
либо выполнять полное транзакционное переключение с restart и rollback.

### U05 Ошибки действий с профилями не отображаются

В `profile-bindings.js:12` выбор, открытие, скачивание и удаление вызывают
асинхронные actions вне общего обработчика ошибок. Например, ответ 422
«Профиль не прошёл проверку Xray» (`profiles.go:289`) завершает promise ошибкой,
а сообщение страницы остаётся прежним. В приложении нет общего обработчика
`unhandledrejection`, который показал бы причину. Эти действия нужно подключить
к общему механизму прогресса, блокировки повторного клика и отображения ошибки.

### W01 Точка отката мастера исчезает при обновлении страницы

Снимок исходного конфига, DNS и firewall хранится только в `state.setupSnapshot`
(`setup-model.js:178`). При reload новый state содержит `null`; восстановить
исходный общий снимок через мастер нельзя. Особенно существенно это после
частичного выполнения, когда уже изменён Xray или DNS. Обещание точки отката
в `setup-view.js:514` не объясняет срок её жизни. Backend копии отдельных
операций не восстанавливают весь сценарий мастера одним действием.

Нужно хранить защищённый снимок и идентификатор операции на роутере, восстанавливать
их при повторном входе и удалять только по понятной политике завершения.

### W02 Неполная проверка превращается в сообщение о работающем подключении

Backend действительно выполняет функциональные проверки DNS/VPN. Однако
`compareRuntimeHealth()` проверяет регрессии относительно прежнего состояния;
при отсутствии положительного baseline он допускает `state:inconclusive`
с `ok:true` (`runtime_health.go:247`, `:281`, `:289`). Это позволяет сохранить
настройки при неопределённом внешнем состоянии, но не доказывает рабочий VPN.
`runSetupWizard()` проверяет лишь `apply.ok` (`setup-actions.js:154`) и завершает
с `phase:complete`; `setup-view.js:504` сообщает «Подключение работает».

Условие воспроизведения — первичная настройка без ранее работавшего VPN,
неподтверждённый транспорт нового сервера и успешные остальные этапы. Следует
показывать неполную проверку отдельно и подтверждать выбранное подключение
перед утверждением о его работоспособности. Предупреждение о неполной проверке
сохраняется в подробностях шага, но противоречит безусловному итоговому тексту.
Probe реального мастера и view подтвердил `ok:true / complete` и этот текст
при `restart.health.state:inconclusive`.

### I04 Ссылка из HTTPS LuCI ведёт на неподдерживаемый HTTPS адрес

LuCI launcher наследует `window.location.protocol` (`dashboard.js:38` и
`scripts/install-openwrt.sh:559`). При HTTPS LuCI получается
`https://192.168.50.117:9090/`, хотя `app.go:117` запускает обычный HTTP
`ListenAndServe`. Переход не открывает панель. Нужно явно использовать протокол
панели либо настраиваемый внешний URL при наличии HTTPS reverse proxy.

### I05 Зеркало из инструкции не используется при установке

Пример в `README.md:392` передаёт `RUOPENRAY_DOWNLOAD_MIRROR` и
`RUOPENRAY_MIRROR_PREFIX`. Скрипт записывает их в UCI (`install-openwrt.sh:279`),
но сам бинарник и checksum скачивает прямо из `$url` (`:198`). При недоступном
GitHub этот пример не помогает установить панель. Следует применять mirror
к загрузке бинарника и явно описать независимый путь получения доверенного
checksum; учесть также загрузку самого install script.

### M02 Очистка geo копий пропускает новый формат

При сохранении backup `geo_transaction.go:146` создаёт каталог
`BackupDir/geo-transaction-*` с прежними DAT файлами. `cleanupGeoBackups()`
в `geo_update.go:299` пропускает все каталоги и распознаёт только старые
плоские имена. Кнопка очистки возвращает успех с нулём удалений, а новые
копии продолжают занимать место. Go probe подтвердил сохранность файла
в таком каталоге после успешного результата очистки.

Нужно распознавать завершённые geo транзакции, проверять принадлежность пути
и удалять их вместе с содержимым, исключая незавершённые операции восстановления.

## Проверки и воспроизведение

- `node --test tests/*.test.mjs`: 277 из 277 прошли.
- `node tests/frontend-smoke.mjs`: 87 проверок, 67 вариантов рендера прошли.
- `node tests/frontend-app-boot.mjs`: прошёл.
- `go test ./...`: все пакеты прошли. Первоначальный запуск в Windows sandbox
  дал отказы доступа к временным файлам и loopback соединениям; повторный запуск
  вне sandbox прошёл. Эти первоначальные ошибки не отнесены к дефектам проекта.
- Изолированные probes подтвердили утечку DoH пароля, сброс локального порта,
  игнорирование необходимости restart профиля, удаление при переименовании,
  ошибку первой установки ядра, неверный итог обновления, пропуск geo копий,
  потерю снимка мастера, ссылку LuCI и успех мастера при неполной проверке.

Локальные диагностические артефакты находятся в игнорируемом каталоге
`.private/audit-ui-install-update-20261104/`. Они не содержат рабочих паролей
или конфигураций стенда. Команды для повторения:

```powershell
node .private/audit-ui-install-update-20261104/ui-probes.mjs
node .private/audit-ui-install-update-20261104/install-ui-probes.mjs
& .private/audit-ui-install-update-20261104/run-updates-probes.ps1
```

Go probes добавляются через overlay во временное представление пакета,
без изменения продуктовых файлов. Их успешный результат означает
воспроизведение описанного дефекта, а не его исправление.

При исправлении сначала закрыть U01, U02, I01 и I02. Затем восстановить
сценарии первого запуска, применения профилей и достоверный итог обновлений.
Проверка фактической установки, обновления и аварийного отката на OpenWrt
остаётся необходимым этапом приёмки соответствующих исправлений.
