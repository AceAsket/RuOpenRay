# Горячее применение правил Xray

В «Сценарии и правила → Правила» кнопка «Подготовить локальный API» добавляет
`RoutingService` в черновик. Существующий API используется только с явным
loopback IP и портом; без API создаётся `127.0.0.1:10086`.
Подготовка не меняет активную конфигурацию и не запускает службы.
Один раз примените этот черновик обычным способом с перезапуском Xray.

Затем обычная кнопка «Применить изменения» выбирает горячий путь, если:

- изменился только `routing.rules`, включая добавление, удаление, порядок,
  домены, IP, порты, устройства и выбор существующего выхода;
- остальная конфигурация, включая `domainStrategy`, DNS, inbounds/outbounds,
  observatory, policy и параметры API, совпадает с сохранённой;
- профиль не содержит балансировщиков или routing script;
- работает единственный Xray 26.10.21 или новее на Linux с одним config-файлом;
- запущен установленный бинарник, его PID/start time и принадлежность сокета
  локального API подтверждены, а список правил API соответствует исходному.

При проверке единственного процесса краткие команды `xray api`, `version` и
`help` не считаются вторым ядром. Опрос статистики панели может выполняться
одновременно с горячим применением; отдельный запущенный Xray по-прежнему
переключает применение на обычный путь.

Проверка всего конфига настоящим Xray, Geo Doctor, backup, ревизии черновика,
запись активного конфига и профиля сохраняются. Выполняется одна команда
`xray api adrules --append=false` с полным списком правил через stdin.
Удаление правил по одному и окно с пустым списком не используются.
После RPC проверяются порядок, `ruleTag`, направления правил и прежний процесс.
`ListRule` не возвращает полные условия: предполагается, что маршрутизацией
этого процесса управляет RuOpenRay, без параллельного внешнего API-клиента.

Новые соединения используют обновлённые правила. Уже открытые TCP/UDP-сессии
сохраняют прежний выход. Горячий путь не перезапускает Xray, DNS или firewall
и не сбрасывает статистику. Отключение счётчиков сохраняет RoutingService.

Если предварительная проверка недоступна, выполняется обычный перезапуск.
На полную замену правил и API-откат отводится по 20 секунд ожидания RPC,
на процесс CLI с чтением и сборкой конфигурации — по 30 секунд.
При ошибке уже начатого RPC повторного применения кандидата нет: ошибка может
означать потерянное подтверждение после успешной замены. Восстанавливаются
старые правила целиком и файл конфигурации, затем проверяется результат.
Если API-откат не подтверждён или процесс сменился, используется обычный
перезапуск с предыдущей конфигурацией. Черновик не удаляется при неудаче.
При такой аварийной ветке сохранность открытых соединений не гарантируется.

Изменения серверов, DNS, балансировщиков, стратегии разрешения доменов и
остальных параметров по-прежнему требуют обычного применения. Полная замена
через API пересоздаёт балансировщики, поэтому горячее применение для профилей
с ними пока исключено, даже если меняется только правило.

Используются штатные [RoutingService и adrules](https://xtls.github.io/en/config/api.html#routingservice).
Семантика предварительной сборки и атомарной замены списка проверена по
[ReloadRules Xray 26.10.21](https://github.com/XTLS/Xray-core/blob/v26.10.21/app/router/router.go)
и 26.10.31. Никакие исходники Xray в RuOpenRay не копируются; вызывается CLI
установленного ядра. Тест с отдельным настоящим ядром проверяет старый TCP
поток, новые выходы и откат после имитации потерянного подтверждения.
