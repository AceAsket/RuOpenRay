# Проверка AdGuard Home перед переносом

Пилот на VM `192.168.50.117` завершён 6 октября 2026 года. На ней установлена панель `0.5.0-test.adguard+e1c85ad`, AdGuard Home 0.107.79 и исходный Xray 26.3.27. Защита и автоматическая синхронизация bootstrap включены. Рабочий роутер `192.168.50.1` проверен через SSH без изменения его настроек или перезапуска сервисов.

## Что реализовано

- DNS → «Рекламорезка»: состояние сервиса, статистика, выключение/включение защиты, проверка домена, добавление/удаление исключений. Результаты проверки переведены на русский; после изменения настроек прежний результат сбрасывается.
- Bootstrap автоматически собирается из активной конфигурации, профилей и кандидатов подписок. Он позволяет разрешить имена VPN-серверов при остановленном Xray. При выключении автоматизации последнее поколение сохраняется для следующего запуска.
- Синхронизация сохраняет чужие upstream и исключения. Ошибка API AdGuard останавливает применение нового VPN-конфига; предусмотрены откат и восстановление частично записанного поколения.
- Защита от активации профиля, который удаляет необходимый локальный SOCKS-вход. Обнаружение TLS-транспорта в диагностике не предлагает ошибочно использовать его как обычный DNS.
- Проверки подписок выполняют HTTP через локальный SOCKS. Исправлен воспроизводимый ложный 503 от промежуточного HTTP-прокси Xray при коротком ответе VLESS WebSocket; десять повторных проверок прошли.
- Новые конфигурации AmneziaWG используют `streamSettings.sockopt.domainStrategy`, сохраняя mark 20992. Старый параметр `freedom.settings.domainStrategy` больше не генерируется.

## Параметры для переноса на рабочий роутер

Аудит обнаружил arm64, Xray 26.3.27, около 6 ГБ свободного места, установленный и остановленный AdGuard Home 0.107.56. Его штатная конфигурация использует DNS 3053, HTTP 3000 и пока не содержит API-пользователей. Она не заменялась конфигурацией пилота.

| Параметр | Пилот | Рабочий роутер / план |
| --- | --- | --- |
| Локальный SOCKS Xray | 127.0.0.1:10808 | Существующий 127.0.0.1:20170 без авторизации |
| Порт 10535 | TLS-транспорт Google | Уже занят действующим DNS Xray по TCP и UDP |
| DNS нового AdGuard | 127.0.0.1:10536 | Предлагается тот же свободный порт |
| TLS-транспорт Google / Quad9 | 10535 / 10537 | Предлагаются свободные 10537 / 10538 |
| API пилотной интеграции | 3001 | Свободный 3001; управление панели через loopback |

Из-за различий портов файлы VM нельзя копировать на рабочий роутер без адаптации. Для переносимой связки проверенной версии 0.107.79 нужно использовать arm64-бинарники, отдельные конфигурацию/данные и сервис; существующий сервис GL.iNet учесть при автозапуске. Нельзя запускать два экземпляра AdGuard на одних портах или автоматически включать его прежнюю конфигурацию без авторизации API.

Для Google и Quad9 в DoH stamps порт TLS provider name меняется на 10537/10538; адрес bootstrap остаётся 127.0.0.1. SOCKS-outbound транспорта указывает на 20170. Порт 10535 и текущий DNS сохраняются до окончания проверки новой связки.

Наличие SOCKS само по себе не гарантирует VPN. В текущей маршрутизации рабочего роутера первый подтверждённый маршрут для IP DoH-провайдеров — direct; более ранние доменные правила зависят от sniffing. Перед переключением dnsmasq нужно явно обеспечить маршрут DoH в выбранный proxy и проверить его фактически. Эту проверку повторяют при смене профиля; простая копия конфигурации транспорта её не заменяет.

## Последовательность переноса

1. Сохранить панель, её данные, конфигурации/ядро Xray, geosite.dat, DHCP, AdGuard и службы автозапуска. Подготовить независимый SSH и возврат dnsmasq к прежнему DNS.
2. Установить панель и подготовить AdGuard с транспортом на свободных портах, сохранив действующий DNS до проверки. Настроить локальный API с авторизацией.
3. Подключить интеграцию к API, синхронизировать bootstrap из реальных профилей/подписок. Проверить маршрут DoH через выбранный VPN и возврат после смены профиля.
4. Проверить новый AdGuard напрямую: записи всех типов, фильтры, исключения, отключение защиты и HTTPS через рабочий VPN.
5. Переключить только DNS upstream dnsmasq на AdGuard, проверить реальных LAN-клиентов, IPv6 и диагностику. При отказе вернуть прежний DNS независимо от панели.
6. Отдельно проверить автозапуск и восстановление VPN. Обновление ядра проводить отдельным шагом, чтобы откат DNS и ядра оставался однозначным.

Рабочая конфигурация и подготовленная копия содержат секреты и хранятся только в игнорируемом локальном каталоге `.private`. В публичном репозитории сохранены результаты и инструкция. Описание API, владения настройками и восстановления: [adguard-integration.md](adguard-integration.md).
