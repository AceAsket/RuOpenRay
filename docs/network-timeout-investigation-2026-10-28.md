# Разбор таймаутов приёмки 28 октября 2026

## Вывод

Найдены независимые проблемы: продолжительное ожидание выбранного Google DoH,
периодические зависания соединений через немецкий VPN и слишком короткий лимит
части диагностических запросов. У Quad9 отдельно воспроизведены сбросы новых TLS
соединений. Одна общая причина для всех пяти неуспешных раундов не доказана.

Повторные тесты локализуют проблемы, но не заменяют новую длительную приёмку.
Настройки, службы и рабочие маршруты `.1` при расследовании не менялись.

## Область и методика

- Исходный прогон: 1802,9 с, 31 раунд, 26 успешных. Фактически установленный
  source тогда был `b08a8b7`: ограничения SDK-кеша описаны в
  [плане приёмки](reliability-implementation-plan.md#итог-испытаний-28-октября).
- Дополнительные испытания: `.117`, OpenWrt 25.12.4 x86_64, Xray 26.10.21,
  AdGuard Home 0.107.79, панель RC4 r8 с подтверждённым source `ede8c53`.
- Отдельные Xray-процессы с копиями профилей, отдельными SOCKS-портами и debug
  логами. Действующий профиль и его Firefox fingerprint сохранялись.
  Сравнивались адрес сервера по имени и закреплённый IPv4, TLS 1.2/1.3/auto,
  разные HTTPS-цели, новые и повторно используемые DoH-соединения.
- Пробы записывали фазу DNS/TCP/TLS/первого байта и исходную ошибку. DNS-запросы
  использовали уникальные имена, чтобы не ограничиться проверкой кеша.
- На `.1` читались конфиг и access log, выполнялся ограниченный пассивный захват
  заголовков пакетов на WAN. Службы не перезапускались, firewall не менялся.
  На `.117` установлен диагностический пакет tcpdump с libpcap.
- Для контроля трафик отправлялся через SSH `direct-tcpip` с `.1` на фиксированный
  IP удалённого сервера. OUTPUT `.1` не перехватывается, поэтому этот путь
  обходит прозрачный Xray `.1`, сохраняя тот же WAN. Тестовый Xray на `.117`
  и удалённый VPN-сервер в VPN-пробах остаются участниками соединения.
- В отдельном сравнении использован официальный Xray 26.9.9, сверенный с
  архивом SHA-256 `1eb9175d0f0a8f8149c9230a7fc5ae66ce332ed20a53155ce61fe62e3f58b7df`.

Сырые конфиги, адреса VPN, packet captures и журналы лежат только в игнорируемой
`.private/network-timeouts-20261028/`. Они не входят в публикацию.

## DNS: найден именно исходный неуспешный запрос

В RAM-журнале AdGuard сохранился уникальный запрос раунда 24 исходного прогона:

| Поле | Значение |
| --- | --- |
| Начало по журналу, UTC | 2026-10-28 16:26:10.651 |
| Выбранный upstream | `https://8.8.8.8:443/dns-query` |
| Время обработки | **30 058,3 мс** |
| Кеш / число ответов | false / 0 |
| Лимит клиента в исходном прогоне | **8 с** |

Следовательно, тест прекратил ожидание раньше завершения upstream-запроса.
Поле `NOERROR` при нулевом ответе в этой записи не является подтверждением
успешного разрешения имени. Среди 34 найденных запросов с меткой `soak-`
других запросов дольше секунды не было.

Во время исходного прогона на `.117` использовались `upstream_mode: load_balance`, `upstream_timeout: 10s`,
список fallback пуст. DNS идёт dnsmasq → AdGuard → DoH напрямую, без Xray.
AdGuard 0.107.79 использует [dnsproxy 0.83.2](https://github.com/AdguardTeam/AdGuardHome/blob/v0.107.79/go.mod).
Его [DoH-клиент](https://github.com/AdguardTeam/dnsproxy/blob/v0.83.2/upstream/doh.go#L144-L175)
после первого запроса через ранее созданный HTTP-клиент допускает ещё две
попытки при подходящей ошибке, в том числе таймауте. У каждой попытки
[собственный HTTP timeout](https://github.com/AdguardTeam/dnsproxy/blob/v0.83.2/upstream/doh.go#L403-L413).
Наблюдаемые 30,06 с согласуются с тремя ожиданиями по 10 с; это вывод по
длительности и исходникам, записи каждой старой попытки в сетевом захвате нет.

Первопричина того единственного зависания пути к Google ретроспективно не
установлена. В новых сериях Google прошёл 50/50 холодных/тёплых проб и ещё
140/140 проб с IP/SNI и разными TLS key exchange. Постоянная недоступность
Google или общая неисправность локального DNS этим не подтверждается.
75 свежих запросов через dnsmasq UDP/TCP и AdGuard UDP прошли полностью,
максимум — 852 мс.

### Независимая проблема Quad9

При новых TLS-соединениях к `9.9.9.9:443` воспроизводятся быстрые ошибки EOF
на TLS handshake. В пассивном захвате WAN есть соответствующие TCP RST до
первого TLS-ответа. Наличие RST не доказывает, что его отправил именно сервер
Quad9: вмешательство промежуточного оборудования не исключено.

| Путь к Quad9, серия по 65 запросов | Успех | Ошибка TLS EOF |
| --- | --- | --- |
| Через LAN `.1`, URL с IP | 62/65 | 3 |
| Через LAN `.1`, с SNI | 61/65 | 4 |
| Через SSH в обход Xray `.1`, URL с IP | 62/65 | 3 |
| Через SSH в обход Xray `.1`, с SNI | 60/65 | 5 |

В отдельных сериях ошибки были и с post-quantum key exchange, и с обычным
X25519. Смена только SNI или отключение PQ не доказаны как исправление.
Сбросы остаются при обходе Xray `.1`; таблица его правил не нужна для их
возникновения. Эти новые ошибки Quad9 нельзя приписывать старому запросу
раунда 24: тот был адресован Google.

## VPN: короткий лимит и реальные зависания

### Ограничение первоначальной методики

Пробы с принудительной версией TLS ждали лишь 4 с. В повторных тестах есть
успешные HTTPS-запросы через DE длительностью **4,5–6,7 с**, включая TLS
handshake. Такие запросы прежняя проба сочла бы неуспешными.

Это объясняет возможность неполных TLS-проб без полного отказа VPN, но не
доказывает причину каждого старого раунда 0/2. В новых сериях встречаются и
настоящие таймауты с лимитом 8 с, поэтому просто увеличить лимит недостаточно.

Ещё одна методическая ошибка: запрос без локального SOCKS к gstatic не был
независимой проверкой WAN. Access log `.1` показывает его отправку через DE
по Google-правилу. Внешние подключения самих VPN-серверов направлялись direct;
вложенный VPN для этих подключений не обнаружен.

### Парное сравнение путей

Один и тот же профиль, HTTPS-цель `1.1.1.1/cdn-cgi/trace`, лимит 8 с:

| VPN / путь к серверу | Успех | Таймаут TLS |
| --- | --- | --- |
| DE, обычный LAN-путь через `.1` | 64/65 | 1 |
| DE, SSH в обход Xray `.1` | 62/65 | 3 |
| FI, обычный LAN-путь | 65/65 | 0 |
| FI, SSH в обход Xray `.1` | 65/65 | 0 |

По debug-логам отдельного Xray различаются два случая:

1. Внешнее подключение/Reality до DE не готово вовремя. Воспроизведено ожидание
   **16,1 с**; в другой пробе туннель появился через **79,5 с**, уже после
   повторного dial и ухода тестового клиента. Эти длительности не являются
   временем ответа целевого сайта.
2. Внешний DE-туннель готов за **116–154 мс**, но внутренний HTTPS handshake
   с целевым сайтом не завершается за **8 с**. Такие случаи были и через SSH.

То есть есть задержки как до готовности туннеля, так и после неё. Вторая группа
не объясняется разрешением имени VPN-сервера: путь SSH закреплён на IP.
Исторические запросы A/AAAA имён DE/FI, найденные в AdGuard, также были быстрыми
(17–144 мс), без задержек дольше секунды.

Это локализует сбои в соединении с DE/через DE, но не позволяет выбрать между
удалённым сервером, транзитной сетью и общими особенностями Reality-клиента.
Без логов/захвата на удалённой стороне объявлять виновным провайдера нельзя.
Успех FI в новых сериях не отменяет старую неполную FI-пробу.

### Проверка зависимости от версии Xray

Одинаковый DE-профиль с исходным Firefox fingerprint, SSH-путь, по 80 запросов:

| Ядро | Успех | Таймаут 8 с |
| --- | --- | --- |
| 26.10.21 | 80/80 | 0 |
| 26.9.9 | 77/80 | 3 |

На старом ядре также наблюдались долгие внешние подключения. Это контрпример
гипотезе «таймауты появились только из-за нового ядра». Серия не доказывает
отсутствие любых регрессий и не устанавливает статистическое преимущество
новой версии.

Экспериментальная замена fingerprint на Chrome оказалась неудачной на обеих
версиях; короткие серии остановлены и исключены из оценки рабочего Firefox
профиля. Менять действующий fingerprint на Chrome по этим тестам нельзя.

## Что остаётся неизвестным

- Для исходных SOCKS-сбоев раундов 11/12 harness сохранил только
  `CalledProcessError`, потеряв stderr и код curl. Причину каждого из них
  восстановить достоверно нельзя. Найденные новые DE-сбои — воспроизведение
  класса проблемы, а не доказанная расшифровка этих двух старых событий.
- Точный сетевой источник старого зависания Google и новых Quad9/DE-сбоев
  не установлен. В последующем [серверном расследовании](vpn-server-timeout-investigation-2026-10-28.md)
  собраны двусторонние captures: новые события разделены на системный DNS VPS
  и задержки внешнего TCP до DE. Конкретный транзитный узел не определён;
  эти данные не расшифровывают каждый старый сбой.
- Новый полностью успешный длительный прогон после устранения причин пока
  не выполнен. Статус исходной приёмки остаётся **26/31**.

## Следующие действия перед повторной приёмкой

1. На `.117` отдельно проверить `parallel` для независимых DoH upstream и
   ограничение общего времени разрешения с учётом повторов. Этот режим
   [отправляет запросы параллельно](https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration#configuration-file),
   поэтому один зависший upstream не должен задерживать ответ исправного.
   Обязателен тест с намеренно недоступным upstream; DoH должен остаться direct.
   Одна замена Google на Quad9 проблему надёжности не решает.
2. В приёмке сохранять исходные ошибки и времена фаз, отдельно оценивать TLS
   1.2/1.3 и общую доступность. Проверять несколько целей, отличать задержку
   от полного отказа. Сохранять результаты до следующей пробы, включая DNS.
3. Для DE проверить удалённый сервер/путь; протестировать FI как резерв с
   несколькими целями и защитой от частых переключений. Не менять рабочий
   маршрут автоматически на основании одной удачной серии.
4. Повторить длительную приёмку подтверждённого SDK-артефакта, включая отказ
   одного DoH upstream и основного VPN. После этого отдельно решать перенос
   на `.1`; текущий отчёт не является разрешением на перенос.

## Завершение диагностики

Отдельные probe-процессы, временные SOCKS-входы, SSH-туннели и captures
остановлены; проверенный временный каталог `.117` удалён после копирования
результатов. Рабочие Xray/AdGuard сохранили PID. SHA-256 конфигов Xray, панели,
DHCP, сети, firewall и AdGuard совпали с исходными; API active config и draft
также совпали. Финальные DNS-запрос через dnsmasq и HTTPS через живой SOCKS
успешны. tcpdump/libpcap на `.117` оставлены для последующей диагностики.

Продолжение расследования и новый SDK-прогон описаны в
[приёмке RC4 r9](reliability-acceptance-rc4-r9-2026-10-28.md): отказ одного DoH
проверен, на `.117` включён parallel, но отдельные VPN-таймауты сохраняются.
Далее выполнена [проверка непосредственно на DE/FI VPS](vpn-server-timeout-investigation-2026-10-28.md):
подтверждены пятисекундные DNS-задержки и отдельный сбой внешнего TCP до DE
при быстром ответе Xray/nginx. Исправлена интерпретация IP-контроля FI:
server-side sniffing возвращал назначение к домену, поэтому удалённый DNS
этой старой пробой не исключался.
