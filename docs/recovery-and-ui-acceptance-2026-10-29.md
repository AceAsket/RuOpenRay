# RC4: восстановление после аварии и массовые действия с правилами

Работы выполнены в `dev`, исходный код пакета — `8b64a76` (основной пакет `c8489dd`
и дополнительная проверка отката отключения firewall).
Испытания и установка выполнены только на тестовой VM `192.168.50.117`.
На `.1` в этом этапе ничего не менялось, цепочка fragmentation сохранена.
Дата отчёта указана по рабочей станции (Москва); часть исходных журналов
роутера содержит предыдущую дату UTC.

## Правила и иконки

- SVG из каталога показывается изолированным `<img>`. Для старых иконок без
  `xmlns` добавляется пространство имён SVG: браузер теперь распознаёт отдельный
  XML-документ. Санитизация и изоляция SVG сохраняются.
- Отметить можно группу целиком или отдельные строки внутри неё. Частичный
  выбор отображается в checkbox группы. «Выбрать показанные» учитывает фильтры
  и текущий лимит отображения. Служебные правила не включаются в массовый выбор.
- Нижняя панель выбранных правил содержит смену сервера, создание группы,
  отключение, удаление и снятие выбора. Смена сервера допускает разные исходные
  назначения; предпросмотр показывает область и число затронутых правил.
- Пустой выбранный набор больше не превращается в замену всех правил.
  Перед отключением полный набор правил сохраняется на сервере. Ошибка записи
  или превышение лимита архива 200 записей оставляет черновик без изменений;
  тихое обрезание архива устранено.

В изолированной панели на `.117` проверены две группы по два правила и общий
маршрут. Смена назначения трёх выбранных строк из разных групп оставила
четвёртую строку на прежнем сервере. Отключение второй группы сохранило её две
строки с разными назначениями в архиве. Фильтр по одному домену позволил
поменять только его сервер; соседнее правило и общий маршрут сохранились.
После завершения автосохранения и перезагрузки страницы черновик и архив
сохранились, активный конфиг изолированной панели не менялся. Обе исходные SVG
без `xmlns` загрузились как изображения с ненулевыми размерами.

Автосохранение черновика имеет существующую задержку 650 мс: немедленная
перезагрузка до отправки запроса может потерять последнее изменение. В приёмке
сначала проверялась запись на сервере. Защита от закрытия вкладки с ещё
неотправленным черновиком остаётся отдельным улучшением.

## Долговечные журналы и восстановление

До live-изменений firewall/geo сохраняются журнал и резервные копии с SHA-256.
Файлы и каталоги синхронизируются на диск. При запуске панели и перед следующей
мутацией незавершённый журнал восстанавливает прежнее состояние. Повторный
сбой посреди отката допускается: уже восстановленный файл сверяется по хешу.
Повреждённые снимки и посторонние пути отклоняются, журнал сохраняется.
До восстановления проверяются все снимки, чтобы повреждение последнего файла
не приводило к частичному восстановлению предыдущих.

Завершённый журнал сначала атомарно выводится из пространства pending, затем
удаляется: прерванная очистка не должна восприниматься как незавершённый commit.
У firewall выбирается обратный batch с учётом отсутствующей после reboot
таблицы ядра. Изменяется только таблица RuOpenRay и принадлежащие ей маршруты.

Обновление панели сохраняет BootID и PID независимого watchdog. Init запускает
отдельный shell-helper **до исполнения нового бинарника**: после аварии он
проверяет хеши и возвращает старую панель, даже если кандидат не запускается.
Обычный restart действующего watchdog не отменяет его проверку готовности.
APK и shell installer устанавливают одинаковый helper, зависят от `jsonfilter`
и выполняют `sync` перед запуском установленной службы.

Перед испытанием остановлена только тестовая VM и сделана проверенная по SHA-256
холодная копия её диска на гипервизоре. Остальные VM и гипервизор не перезапускались.

| Точка настоящего отключения питания VM | Автовосстановление панели | Проверка после загрузки |
| --- | --- | --- |
| После успешного kernel commit nft, до продвижения файлов | Панель 16,0 с; DNS 16,2 с | Исходные файлы/таблица, DNS UDP+TCP 2/2, HTTPS через рабочий SOCKS 2/2 |
| После продвижения первого из двух DAT | Панель 16,0 с; DNS 16,2 с | Оба исходных DAT по SHA-256, DNS UDP+TCP 2/2, HTTPS 2/2 |
| После замены панели и запуска watchdog, до подтверждения готовности | Панель 16,0 с; DNS 16,2 с | Исходный бинарник, результат `interrupted_rollback`, DNS UDP+TCP 2/2, HTTPS 2/2 |

Таблица содержит повторную серию на установленном SDK r11 с тестовым harness,
скомпилированным из тех же исходников. В предыдущей серии на подготовительном
кандидате полный набор контрольных запросов завершался за 16,3–17,7 с.
Во всех трёх зачтённых испытаниях совпали active config, draft, профили,
учётные данные и защищённые настройки роутера. Журналы pending были обработаны.

При первом отдельном отключении с r11 панель восстановилась и защищённые хеши
совпали, но первый UDP DNS probe не получил ответа за 8 с. Последующие шесть
DNS-проверок (UDP/TCP, три домена) и HTTPS через VPN прошли. Причина единичного
пропуска не доказана. В повторной серии выше DNS был готов без повторов, примерно
через 0,2 с после панели. Первоначальный таймаут сохранён отдельно в evidence;
его нельзя исключать из общей оценки сетевой устойчивости.

При первой подготовке ручная установка тестовых файлов не была завершена
явным `sync`: после отключения часть только что скопированных файлов оказалась
пустой. Эта попытка не зачтена. Файлы восстановлены, проверены хеши и native
валидация, добавлен обязательный `sync`; таблица содержит последующие корректно
подготовленные испытания. Это проверка выбранных точек потери питания гостя,
не сертификация физического накопителя/хоста или каждой инструкции APK upgrade.

Незавершённая очистка может оставлять безопасные orphan staging/finished-файлы.
Автоматическая сборка таких остатков пока не реализована. Повреждённый журнал
блокирует дальнейшие мутации; его разбор требует SSH, отдельного экрана нет.

## Реальный включённый cron

Через API включено временное ежедневное geo-расписание (повторено на SDK r11).
Настоящий `crond`
запустил установленную панель с фактическими DataDir/ActiveConfig. Из локального
контролируемого HTTP-источника получены два валидных DAT больше 1 КиБ; оба
продвинуты, SHA-256 совпали. Native Xray принял конфигурацию с категориями из
обеих баз; после restart получен `health=healthy`. Active/draft и защищённые
настройки совпали. Исходные расписание, crontab и базы восстановлены.
Доступность внешних geo-источников этим тестом не доказывается.

## GitHub без fragmentation

На `.117` запущен отдельный Xray с тем же NL-профилем и Firefox fingerprint,
что в предыдущем сравнении. Рабочие профили не менялись. Запрашивались
`github.com/robots.txt`, `github.com/favicon.ico` и `README.md` из закреплённого
коммита RuOpenRay на `raw.githubusercontent.com`. Лимит ответа 2 МиБ, timeout 8 с;
файл прочитан целиком и сверен с Git по SHA-256.

| Режим | TLS | HTTP 200 / запросы | Остальные результаты |
| --- | --- | --- | --- |
| Fragmentation выключена | 1.2 | 58/60 | Два таймаута: robots и favicon |
| Fragmentation выключена | 1.3 | 60/60 | Ошибок не обнаружено |
| Fragmentation включена, контроль | 1.2 | 30/30 | Ошибок не обнаружено |
| Fragmentation включена, контроль | 1.3 | 28/30 | Повреждённая версия TLS record и таймаут raw-файла |

Все 40/40 загрузок README без fragmentation совпали с исходным Git-файлом.
HTTP 403 в этой серии не было. Ошибка TLS с fragmentation воспроизведена на
обычном web-контенте. Два таймаута без неё остаются; устойчивость всей сети
не объявляется подтверждённой, настройки `.1` не меняются.

## Завершение

Временные UI/HTTP-процессы, их каталог, локальный SSH forward и вкладка проверки
закрыты после сохранения evidence. Удалены только проверенные по хешам тестовые
geo-базы/staging и четыре архива CRASHBASE. GeoDir возвращён к исходному отсутствию,
расписание и crontab — к исходным байтам. Cold backup диска VM сохранён на
гипервизоре. Тестовый результат `interrupted_rollback` оставлен как история
действительно выполненного аварийного восстановления панели.

После очистки active/draft, профили, учётные данные, сеть, DNS и AdGuard совпали
с исходной контрольной точкой. Финальный smoke: DNS UDP/TCP 2/2, HTTPS через
рабочий SOCKS к двум целям в трёх раундах 6/6. Тестовых listeners не осталось.
Результаты прежней длительной приёмки не заменяются этим коротким smoke;
два GitHub-таймаута и единичный первый DNS timeout после boot остаются в отчёте.
