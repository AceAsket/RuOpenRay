Проверки выполнены на отдельной VM `192.168.50.117`: OpenWrt 25.12.4 x86_64, ядро Linux 6.12.87, Xray 26.3.27, AdGuard Home 0.107.79. Производственный роутер `192.168.50.1` в рамках B4-пилота не изменялся. Общий перехват физической LAN не включался; дополнительно проверен прозрачный перехват изолированного виртуального клиента. Существующие неприменённые изменения панели сохранились.

## Установка и изоляция

Использован официальный B4 1.85.0, архив `b4-linux-amd64.tar.gz`. SHA-256 проверен по digest релиза GitHub:

```text
4cf02a7967369c62ec592341a58b66f34b65cb83b352d57aca16b22ae38cc4f3
```

Установлены подписанные пакеты OpenWrt `kmod-nfnetlink-queue` и `kmod-nft-queue` под действующее ядро. B4 работает через procd, бинарник `/usr/bin/b4`, конфигурация `/etc/b4/b4.json`, авторизованный веб-интерфейс на порту 7000. API панели обращается к нему только через loopback. Пароли и конфигурации с секретами в Git не сохранены.

Параметры пилота: внешняя NFQUEUE 537–538, два потока, packet mark B4 `32768`, IPv4/IPv6 включены, `system.tables.skip_setup=true`. TUN, SOCKS/MTProto B4, DNS и маршрутизация сетов выключены. Тестовый сет содержит `example.com` и `example.org`, использует TLS record fragmentation; `faking.sni=false` задан явно. Отключение стратегии fake-пакетов само по себе не отключает SNI faking.

Для проверки в Xray временно добавлялись только два доменных маршрута через выделенный `direct-b4` с socket mark `524288`. Остальные правила, VPN и путь DoH сохранялись. Выделенная таблица `inet ruopenray_b4_direct` ограничивала очередь отмеченными TCP 80/443 и UDP 443 и ответами этих соединений. Основной Xray перезапускался только на тестовой VM.

## HTTP/3 и реальные IPv6-соединения

Внутри VM использованы два изолированных namespace: клиент `198.18.0.2` / `2001:db8:51::2` и HTTPS/HTTP/3-сервер `198.19.0.2` / `2001:db8:52::2`. Клиент использует quic-go 0.63.0; HTTP/3 подтверждён ответом `HTTP/3.0` и ALPN `h3`, без перехода на TCP. Проверка сертификата включена, доверие ограничено временным CA тестового сервера. TCP-контроль использует HTTPS с тем же сертификатом.

Проверки выполнены отдельными процессами Xray 26.3.27 и 26.9.9, без замены основного бинарника. Для IPv4 применён штатный шаблон TPROXY; для проверки IPv6 backend временно добавлены отдельный inbound на `::1`, IPv6 policy rule, локальный маршрут `::/0` и `tproxy ip6`. В firewall разрешены только тестовые интерфейсы, адреса и Neighbor Discovery.

| Проверка | Результат на каждой версии Xray |
| --- | --- |
| IPv4 HTTPS и HTTP/3 через штатный TPROXY → `direct-b4`, UDP `off` | Пройдено |
| IPv6 HTTPS через SOCKS → `direct-b4` | Пройдено |

| Завершение каждого прогона | Основные Xray/AdGuard/DoH и их конфиги сохранены; временные процессы, интерфейсы, правила и файлы удалены |

UDP `fake` проверялся с остальными настройками пилотного сета. Это подтверждает доставку HTTP/3 с данной конфигурацией, но не эффективность всех QUIC-стратегий против DPI.

Публичные HTTP/3-запросы к `cloudflare-quic.com` и `www.google.com` дали таймауты как через тестовый `direct-b4`, так и в прямом контрольном запросе с VM. Доступность HTTP/3 через интернет на этом сетевом пути не подтверждена; причина внешних таймаутов не установлена. У VM нет глобального IPv6-адреса и маршрута в IPv6-интернет, поэтому IPv6 проверен между изолированными сетями внутри VM.

### Найденные ограничения перед переносом

1. Штатный native TPROXY генерирует IPv4 inbound, правила `tproxy ip` и IPv4 policy routing. Включение `queue.ipv6` в B4 расширяет обработку уже выбранного выхода, но не добавляет IPv6-перехват LAN в RuOpenRay. До переноса в сеть с IPv6 нужны поддержка IPv6 в генераторе и отдельная проверка bypass, DNS и policy routing.
2. Первые девять UDP-пакетов не обеспечивают постоянный QUIC `reject` за Xray: после исчерпания лимита соединение устанавливается. Удаление лимита в отдельном контрольном тесте предотвращает установление HTTP/3. Эти временные правила удалены; исправление политики очереди в продукт ещё не внесено. Перед использованием `reject` нужно исправить и проверить выбор ограниченной/постоянной UDP-очереди при изменении активных сетов B4. Быстрый переход браузера на TCP через ICMP и режим `drop` отдельно не подтверждены.
3. Обход реального провайдерского DPI, HTTP/3 через интернет, IPv6 WAN и нагрузка рабочего роутера остаются непроверенными. Успех локального теста не заменяет эти проверки.

## Итоговое состояние и возврат

B4 запущен, API подключён. Очередь RuOpenRay выключена, временные доменные маршруты удалены, исходные правила Xray и firewall восстановлены. Выход `direct-b4` оставлен подготовленным в действующей конфигурации и профиле `subscription-test`, но ни одно исходное правило на него не перенаправлено. До ручного выбора маршрутов B4 не обрабатывает пользовательский трафик.

После последнего прогона повторно прошли 28/28 DNS-проверок и 6/6 HTTPS-запросов через DNS VM и основной SOCKS с проверкой сертификатов. Основное ядро осталось 26.3.27; API B4 и фильтрация AdGuard работают. В nftables осталась только исходная таблица `inet fw4`, временных namespace и интерфейсов нет.

Резервные копии на VM находятся в `/etc/ruopenray-ui/backup-b4-pilot/`: `ruopenray-ui.before`, `xray.before.json`, `xray.traffic-before.json`, `profile.before.json`. Возврат требует сначала выключить выделенную очередь, остановить B4 и его автозапуск, затем восстановить нужные конфигурацию/профиль и бинарник панели. Подготовленный выход можно удалить отдельно, если на него больше нет ссылок. Удалять весь ruleset или чужие таблицы не требуется.

Перед переносом на рабочий роутер нужны его собственные проверки модулей ядра, маркировки, портов, VPN, DNS/DoH и реальных клиентов. Файлы с адресами серверов и секретами нельзя копировать или публиковать из пилота без адаптации. Инструкция интеграции: [b4-integration.md](b4-integration.md).
