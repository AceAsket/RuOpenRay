# Проверка Xray перед обновлением

Матрица проекта фиксирует Xray 26.3.27 и 26.9.9. SHA-256 Linux/amd64 архивов закреплены в `.github/workflows/build.yml`. Для локальной проверки задайте `RUOPENRAY_TEST_XRAY` абсолютным путём к официальному бинарнику и выполните:

```sh
go test ./cmd/ruopenray-ui -run 'TestTLSSubscriptionTunnelProbe|TestXrayCompatibility' -v -count=1 -timeout=180s
```

Проверяются реальные VLESS gRPC TLS, Trojan TCP TLS, VLESS WS TLS и VLESS XHTTP TLS; неверные учётные данные и сертификаты отклоняются. Все серверы, сертификаты, назначения и порты временные, трафик остаётся на loopback. HTTP-запрос идёт через туннель: HTTP-сайт на порту VLESS/Trojan не нужен.

## LAN и DNS

В 26.9.9 ограничения Freedom на частные адреса по умолчанию зависят от входящего протокола. Они действуют, в частности, для VLESS/VMess/Trojan; локальные HTTP/SOCKS и dokodemo-door не входят в этот список. Это проверено для HTTP, VLESS и dokodemo-door. Поэтому результат проверки одного входа нельзя переносить на все остальные.

Для удалённого VPN-клиента доступ к нужному локальному ресурсу следует разрешать в `settings.finalRules` соответствующего freedom-outbound, перечисляя конкретные адреса/порты. Не следует разрешать все частные сети без разбора. В тестах разрешается только `127.0.0.1/32`. На старом ядре эти новые правила не обеспечивают ограничения: оно игнорирует неизвестное поле. Ограничения серверного режима должны оставаться также в маршрутизации и firewall.

DNS проверяется изолированно через статический `dns.hosts`, без внешнего резолвера. Для Freedom проверены обе формы настройки `UseIPv4`: прежняя `settings.domainStrategy` и новая `streamSettings.sockopt.domainStrategy`. В 26.9.9 прежняя форма автоматически переносится с предупреждением. При ручной миграции сначала проверьте существующие sockopt и outbound.targetStrategy: нельзя бездумно перезаписать уже заданную стратегию. Сохраните старый конфиг и выполните `xray run -test` обеими версиями перед применением.

Тест dokodemo-door проверяет пересылку TCP к фиксированному локальному назначению. Он не подменяет проверку Linux TPROXY, UDP DNS, IPv6, policy routing и реальных LAN-клиентов. Для смены ядра на роутере нужны отдельное окно обслуживания и такие проверки. Обновление панели этих настроек не меняет.

## Обновления и импорт

Ядро скачивается и сверяется с официальным SHA-256 до изменения сервиса. Новый бинарник сначала проверяет активный конфиг. Обязательная копия прежнего ядра создаётся независимо от флажка сохранения копии; флажок определяет её удержание после успеха. При ошибке перезапуска или проверки процесса выполняется откат. Проверка процесса не гарантирует доступность каждого удалённого сервера и маршрута. При аварийном завершении самой панели или потере питания автоматический откат не гарантирован; путь резервной копии возвращается в результате операции. Замена работающего ядра требует перезапуска и разрывает его текущие соединения.

Импорт отклоняет `allowInsecure=true`/`insecure=true`: обе версии Xray уже удалили этот режим. Нужны корректный сертификат и SNI. Параметры `extra`, `ech`, `echConfigList`, `fm`, `pcs`, `vcn` пока отклоняются с объяснением, чтобы не терять их молча; для них используйте проверенный JSON. Отчёт содержит номера записей и причины, без исходных секретных ссылок. Перед автоматическим применением изменённого сервера проверяется трафик через отдельный процесс Xray к `https://www.gstatic.com/generate_204`; недоступность этого адреса также отменяет применение. Неизменившийся сервер не требует перезапуска. При ошибках автоматического обновления подписки прежние серверы сохраняются; частичный ручной импорт доступен через предпросмотр.

Новые CI-сборки панели: `0.5.0-test.<номер запуска>+<коммит>`; сборки тега сохраняют номер тега. Stable исключает prerelease, Test включает их. Обновление предлагается только при строго большей версии. `dev` и старые `5.0-test-<коммит>` несравнимы: переход с них выполняется контролируемым обновлением панели, без автоматического понижения до старого стабильного релиза.
