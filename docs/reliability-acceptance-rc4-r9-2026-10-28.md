# Приёмка RC4 r9 на тестовом стенде

Все изменения и аварийные испытания этого этапа выполнены только на
`192.168.50.117`. Конфиги и службы `192.168.50.1` не менялись.
Предыдущие причины таймаутов разобраны в
[отчёте расследования](network-timeout-investigation-2026-10-28.md).

## DNS при отказе upstream

Отдельный экземпляр AdGuard Home 0.107.79 запущен с собственными config/work
directory и DNS-портом на loopback. Его кеш отключён. Тестовый HTTPS upstream
принимает TCP и ClientHello, но не отвечает; рабочие upstream — прямой DoH
Google/Cloudflare. Действующий DNS не подменялся этим экземпляром.

| Сценарий | Свежих запросов | Успех | Максимум |
| --- | --- | --- | --- |
| Оба DoH исправны, parallel | 15 | 15 | 117 мс |
| Первый upstream завис, второй исправен | 15 | 15 | 106 мс |
| Второй upstream завис, первый исправен | 15 | 15 | 176 мс |
| Единственный upstream завис | 3 | 0, ожидаемый отказ | 6004 мс |

Время одной попытки — 2 с. Последний сценарий показывает, что суммарное
ожидание из-за повторов может достигать 6 с: настройка не является общим
дедлайном всего DNS-запроса. Контроль не доказывает устойчивость при отказе
всех внешних DNS-серверов или всего WAN.

После теста на рабочем AdGuard `.117` через его API сохранены:

- `upstream_mode: parallel`;
- `upstream_timeout: 2` секунды на попытку;
- общие upstream `https://8.8.8.8/dns-query` и
  `https://1.1.1.1/dns-query`.

Доменные маршруты DNS для VPN bootstrap, фильтры, DHCP, сеть, firewall,
active config и draft сохранены. API AdGuard подтвердил настройки; его PID
и PID Xray при сохранении не менялись. В backup сохранены прежние DNSInfo и
YAML; plain DNS fallback не добавлен. Quad9 исключён из общего списка только
на `.117`, поскольку у него отдельно воспроизводились TLS EOF.

Затем Xray `.117` действительно остановлен: четыре свежих DNS-запроса через
dnsmasq по UDP/TCP успешны, максимум **215 мс**. Xray запущен снова, HTTPS через
живой SOCKS восстановлен. AdGuard продолжал работать, конфиги и draft сохранились.
Таким образом, для этой схемы DNS не зависит от VPN `.117`.

## Реальные DE/FI и управляемый отказ

Отдельный Xray 26.10.21 использовал копии настоящих DE/FI Reality-профилей.
Два локальных TCP relay позволяли прервать соединения только этого экземпляра,
не затрагивая рабочие VPN. Проверялся `leastPing` с selector основного DE и
`fallbackTag` резервного FI. Первый выход — blackhole; прямого выхода нет.
Дождались явного Alive-состояния обоих каналов в `/debug/vars`.

| Сценарий | Сходимость наблюдения | HTTPS-ответы | Выбор по access log |
| --- | --- | --- | --- |
| Оба исправны | 0,10 с после старта ожидания | 3/3 | primary |
| Основной отключён | 2,15 с | 3/3 | backup |
| Оба отключены | 0,15 с | 0/3, ожидаемый отказ | backup, без обхода напрямую |
| Основной восстановлен, резерв выключен | 2,05 с | 3/3 | primary |
| Оба восстановлены | 2,66 с | 3/3 | primary |

Три цели: gstatic generate_204, Cloudflare generate_204 и HTTPS по IP
`1.1.1.1/cdn-cgi/trace`, лимит 8 с на запрос. Приведено время от изменения
тестового relay до требуемых Alive-статусов; это не верхняя граница для любого
вида отказа. В частности, молчаливое отбрасывание пакетов может обнаруживаться
дольше, чем закрытие TCP. Старые соединения failover не переносит.

Observatory в этом тесте проверяет один gstatic URL каждые 2 с; три адреса
выше — проверка передачи трафика, **не** quorum внутри Xray. Порог ошибок и
задержка возврата обычным Observatory не реализованы. В рабочем профиле
балансировщик не включался, auto-failover этих тестовых экземпляров не
является изменением действующих маршрутов. Ограничения описаны в
[документации failover](vpn-failover.md).

## Диагностика и установленный пакет

`tlsStabilitySample` теперь возвращает последнюю фазу
DNS/TCP/TLS/ожидание HTTP/тело и временные отметки от начала запроса. Возвращается
копия timing map под mutex, чтобы поздний callback после отмены не менял
кодируемый ответ. Человекочитаемые ошибки, классификация и проверка сертификата
сохранены. При SOCKS TLS-фаза может включать ожидание удалённого туннеля;
эта метрика не разделяет внешнее Reality и внутреннее HTTPS.

В интерфейсе доступны «Время и фазы запросов» для каждой версии TLS.
Пояснено, что отметки времени не складываются, а upstream-роутер может
маршрутизировать запрос без локального прокси через VPN. Браузером на `.117`
проверены настоящие TLS 1.2/1.3 запросы через FI и без локального прокси,
раскрытие времён и графический флаг FI. Конфигурация при диагностике не применяется.

- Пакет: `ruopenray-ui-0.5.1_rc4-r9.apk`.
- Source: `223dac993fa99c6642d9fc495cfaa71da3e6ba3e`, recipe `75b99d2`.
- SHA-256: `2b359ee6d8701aa24e81a02eee814af2b6ee88be81c576dbb059ec2bfd461927`.
- SDK использовал архив с полным source SHA; встроенные JS/CSS сравнены с Git.
  Загруженный executable совпал с установленным файлом. При APK upgrade
  credentials, profiles, active config, draft, DNS, firewall и PID Xray/AdGuard
  сохранены.
- Успешны Go `./...`, Linux race, 159 frontend-тестов, smoke 87 проверок /
  66 рендеров и app boot. Отдельные тесты воспроизводят отмену TLS handshake,
  ожидание HTTP-заголовков и обрыв тела после HTTP 200.
- CI на `fc2eff3`: [build/race/native Xray/пять архитектур](https://github.com/AceAsket/RuOpenRay/actions/runs/40749333782)
  и [OpenWrt SDK](https://github.com/AceAsket/RuOpenRay/actions/runs/40749334007)
  успешны. Временная попытка сократить SDK kernel defaults отменена после
  проверки его скрытых Kconfig defaults; используется стандартная сборка.

## Мутационные проверки импортов

Добавлены постоянные Go fuzz targets для VPN URI/подписок, бинарных ответов
DNS, путей файлов в backup и SVG каталога. Проверяются отсутствие аварий при
разборе, представимость успешного импорта в JSON, корректность IP-ответов,
сохранение разрешённых границ путей и запрет активных SVG-конструкций.
Короткие прогоны Linux Go 1.26 с двумя workers на цель:

| Цель | Время | Выполнений | Результат |
| --- | --- | --- | --- |
| FuzzShareImport | 60 с | 1 605 660 | PASS |
| FuzzDNSWireAnswers | 61 с | 574 032 | PASS |
| FuzzBackupDestination | 61 с | 628 482 | PASS |
| FuzzCatalogSVG | 61 с | 882 339 | PASS |

Итого 3 690 513 входов. Это не полнота проверки пространства входов:
backup-цель проверяет выбор пути, а не полный restore/символические ссылки;
SVG-цель не заменяет проверку исполнения в браузере; тесты не обращаются к VPN
серверам. Начальные примеры включены в обычный `go test`. Linux race после
добавления targets и [CI с новыми тестами](https://github.com/AceAsket/RuOpenRay/actions/runs/40753033188)
на `1c0ef96` успешны. Новых изменений исполняемого кода в этом коммите нет,
установленный пакет по-прежнему использует source `223dac9`.

## Повторный длительный прогон

Прогон r9 выполняется 31 раунд с интервалом 60 с. В каждом раунде отдельно
сохраняются три HTTPS-цели через DE, FI и рабочий SOCKS, два свежих DNS-запроса
UDP/TCP, ошибки/фазы/времена, PID/RSS и контроль хешей. Сначала результаты
записываются на диск, затем выполняется дополнительная диагностика TLS 1.2/1.3.

Оценки различаются: доступность требует минимум 2/3 HTTPS-целей для каждого
канала, обоих DNS-ответов и сохранности состояния; строгая оценка требует
успеха всех обычных запросов. Целевые пробы TLS учитываются отдельно.
Такую метрику доступности нельзя напрямую сравнивать с исходным 26/31,
где все принудительные TLS-пробы должны были уложиться в 4 с.

Фактическая длительность — **1802,7 с**, 31 раунд. По проверке нескольких целей
доступность сохранена **31/31**; строгая оценка всех обычных запросов —
**28/31**, неуспешны раунды 18, 19 и 29:

| Путь | Запросы | Успех | Таймауты |
| --- | --- | --- | --- |
| Отдельный DE | 93 | 91 | 2 |
| Отдельный FI | 93 | 93 | 0 |
| Рабочий SOCKS, default DE | 93 | 92 | 1 |
| Свежий DNS UDP/TCP | 62 | 62 | 0 |

Два DE-таймаута — gstatic и HTTPS по IP `1.1.1.1`; таймаут рабочего SOCKS —
тоже HTTPS по IP `1.1.1.1`. Все три остановились на клиентской TLS-фазе с
лимитом 8 с. Другие HTTPS-цели в каждом таком раунде были доступны.
Все 28 дополнительных проб API с принудительными TLS 1.2/1.3 прошли, ошибки
API не наблюдались; фазы и времена сохранены. Это отдельная целевая серия.

Active config, draft и контрольные хеши на протяжении прогона сохранены.
В 31 ресурсном снимке PID служб стабильны; максимум RSS панели — **40,2 МиБ**.
Во время этого прогона также использовался браузер, а в конце выполнялись
дополнительные FI-пробы; это не идентичная нагрузка первоначального r4-теста.
Снимки не доказывают непрерывную доступность между раундами.

После прогона выполнен настоящий `POST /api/service` restart: за **6,3 с**
получен `health.state=healthy`, успешны DNS, live SOCKS, два используемых VPN
и WAN-control. Config, draft, DNS, firewall, UI binary и PID AdGuard сохранены.
PID Xray изменился в этом отдельном разрешённом тесте перезапуска.
Все временные Xray/AdGuard/relay/probe-процессы завершены, тестовые каталоги
на `.117` удалены; остаточных тестовых listeners нет. Новые DNS-параметры
parallel / Google + Cloudflare / 2 с сохранены на `.117`.

**Итог:** DNS-проверки этого этапа пройдены; общая сетевая приёмка не полностью
зелёная из-за остаточных VPN-таймаутов. Стабильный релиз и перенос на `.1`
не выполнялись.

### Дополнительные проверки оставшихся VPN-задержек

Пойманный в раунде 18 DE-таймаут имеет более точную причину: по debug-логу
отдельного Xray внешний туннель стал готов через **25,4 с**, тогда как клиент
завершил запрос через 8 с. В раунде 29 туннель стал готов через **17,0 с**.
Поэтому эти случаи не являются только медленным HTTP-ответом целевого сайта.
Отдельный сбой рабочего SOCKS был на HTTPS по IP `1.1.1.1`, без DNS назначения.

У медленных FI-запросов внешний туннель обычно готов за 60–70 мс, а внутренний
TLS handshake завершается примерно через 5 с. Для проверки зависимости от
DNS сравнивались доменное назначение и оба опубликованных IPv4 Cloudflare,
с сохранением тех же SNI и HTTP Host. Все три серии прошли 25/25, но в каждой
было по четыре ответа дольше 4 с; закрепление IPv4 задержки не устранило.
Отдельная серия gstatic с закреплённым IPv4 прошла 24/25.

**Уточнение после доступа к VPS:** этот контроль не исключал DNS на FI.
Его серверный sniffing заменяет IP назначения доменом TLS SNI, поскольку
`routeOnly` не включён. Прямые проверки на VPS затем воспроизвели DNS-ожидание
около 5 с. Полные результаты и отдельно пойманная транспортная задержка DE —
в [серверном расследовании](vpn-server-timeout-investigation-2026-10-28.md).

Контроль размера ClientHello/групп key exchange также не дал исправления:
при обычных настройках Go TLS и при ограничении X25519/P256 — по **39/40**,
соответственно 7 и 9 запросов дольше 4 с. Это экспериментальные ограничения
клиента проверки, рабочие настройки TLS не менялись. Исчезновение проблем
после отключения PQ или замены DNS по этим данным обещать нельзя.

Дополнительные серии не входят в основной счётчик 31 раунда и не скрываются
в его метрике доступности. Они подтверждают остаточную нестабильность FI тоже.
В последующем серверном расследовании собраны captures с обеих сторон и
разделены задержки системного DNS VPS и внешнего TCP до DE. Настройки resolver
VPS пока не менялись; полностью успешная длительная приёмка остаётся открытой.
